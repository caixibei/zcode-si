# Production Troubleshooting

## 执行判据（本技能通用） [S-PTS-01]

- **触发条件**：使用本技能处理其 description 所述任务时。
- **动作要求**：按本技能正文的步骤、约束和输出格式执行；涉及写文件、Git、外部发送、用户确认或其他状态变更时，先满足正文对应边界。
- **判断标准**：本技能要求的输入、步骤、输出/产物和检查项全部完成，并在回复或交付中给出可定位证据；未完成项标明阻断。
- **失败或例外处理**：前置条件不满足、信息缺失或用户未确认时暂停并说明缺失项，不得跳过、伪造或把未验证表述为完成。

## 目标 [S-PTS-02]

把生产问题从“猜测”收敛到“有证据的根因”，并在用户批准前保持只读。适用于 HTTP 接口、定时任务、消息消费者、邮件/短信通知、数据异常、前后端联调、多端行为不一致等生产问题。

不适用于：单纯解释代码、执行已知方案、功能开发。但“验证修复”阶段仍适用。

## 硬约束 [S-PTS-03]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

1. **只读优先**：日志、`SELECT`、配置读取、代码阅读先行。重启服务、删除、更新生产数据、改配置、跑迁移、发真实邮件都必须先获得用户明确授权。
2. **环境对齐**：先确认运行配置（profile/environment）→ 数据源 → 运行进程/容器 → 日志目录 → 部署版本；日志中的进程 ID、数据、快照时间必须与当前环境一致。
3. **事实/假设/推论分离**：日志行、SQL 结果、代码行、配置、用户确认才算事实；其余标注为假设或推论，并给出验证方式。
4. **先反驳再下结论**：至少尝试推翻一次当前最可能的假设，并检查相似接口、环境错配、旧快照、部分失败等替代解释。
5. **批准前不改代码**：分析阶段只输出结论、证据、风险和方案；用户明确批准后才进入修复。
6. **脱敏**：不输出密码、Token、Cookie、连接串、客户邮箱/手机号、身份证号等；日志中的敏感值用占位符。
7. **多入口逐项核查**：涉及多个 Controller/Service/前端事件/定时任务时，逐个列出路径、行号、触发条件和结果；未核查的标为“未覆盖”。

### Phase 1：建立证据基线 [S-PTS-05.02]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

1. 确认环境：运行配置、数据源、进程/容器、日志目录、部署版本。
2. 收集日志：当前日志 + 轮转日志 + 压缩包，按**精确接口名/任务名/异常类名**过滤，不用“发送失败”这类泛化词。
3. 建立时间线：请求开始/结束、线程、traceId/requestId、耗时、操作人。
4. 拿业务 ID：从 ORM SQL 参数、请求体、消息头、日志埋点中提取。
5. 查数据：用业务 ID 查失败行之前使用的字段，确认空值/关联/状态。

详细命令见 `references/log-troubleshooting-playbook.md`。

### Phase 2：提出假设并做判别性取证 [S-PTS-05.03]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。

> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

- 列出 2–4 个假设，按可能性排序；每个假设写清楚“支持证据 / 反对证据 / 最便宜的只读验证”。
- 一次只做一个能改变结论的检查，不做与决策无关的全面扫描。
- 用下表区分证据等级：

| 类型 | 要求 |
|---|---|
| 事实 | 日志行、SQL 结果、代码行、配置、用户确认，能指出来源 |
| 假设 | 明确标注，并写出验证/推翻方式 |
| 推论 | 说明依赖哪些事实或已验证假设 |

### Phase 3：反驳 [S-PTS-05.04]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。

> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

至少执行以下检查，并在输出中说明结果：

- 是否有相似接口/相似错误文案被误命中？
- 日志是否来自旧进程、旧环境、旧快照？
- 是否是部分失败（例如批量操作只成功了一部分、邮件只发给了部分收件人）？
- 是否是数据问题而非代码问题（字段为空、状态不符、关联缺失）？
- 是否是下游/网络/权限/配置问题？
- 代码行号是否与生产部署版本一致？

只有至少两个独立证据源一致，才把假设升级为根因。

### Phase 4：呈现结论 [S-PTS-05.05]

> 触发条件：完成证据基线、假设与反驳后，需要输出结论时。

输出必须包含：

1. **结论**：一句话说明根因，先给答案。
2. **证据链**：时间线 + 日志位置（来源文件与行号）+ 代码 `file:line` + 排查所用 SQL 语句（无数据库触点时写明）+ 数据字段实际值；每条关键结论的三类材料齐全，无法取得的材料标注「未验证：[阻断原因]」。本节是全局证据链要求在排查技能内的落地细化，权威定义见 `~/.zcode/AGENTS.md`「批判性审查」第 9 项；用户要求跳过证据链时按该条第 9 项的确认出口执行。
3. **置信度**：高/中/低，以及为什么。
4. **未验证范围**：缺什么证据、被什么阻断。
5. **修复选项**：最小修复 vs 根治方案，各自影响面与风险。
6. **下一步**：需要用户决定的事项。

用户批准前停在这里，不实现、不改代码、不改生产数据。

### Phase 6：验证 [S-PTS-05.07]

## 风险升级 [S-PTS-06]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。

> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

出现以下任一情况，必须补充调查或独立复核：

- 结论涉及数据一致性、权限、金额、状态流转、工作流、对外契约；
- 未验证前提会改变推荐方案或风险等级；
- 反驳成立，需要新证据；
- 用户将依据结论做不可逆操作；
- 多个入口/多端行为不一致。

## 通用排查路径 [S-PTS-07]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

1. **确认环境**：运行配置 → 数据源 → 进程/容器 → 日志目录 → 部署版本。
2. **找日志**：当前 + 轮转 + 压缩；精确入口；时间窗口。
3. **串请求**：开始/结束、线程、traceId/requestId、耗时、操作人。
4. **拿业务 ID**：ORM `Parameters`、请求体、消息头、日志埋点。
5. **查数据**：失败行之前使用的字段，逐个核对空值/关联/状态。
6. **对照代码**：`file:line`，确认部署版本与源码一致。
7. **异常映射**：NPE=取数/组装；参数异常=校验；SQL 异常=映射/表结构；邮件/网络异常=下游；`NoClassDefFoundError`=构建/依赖。
8. **反驳**：相似入口、环境错配、旧快照、部分失败、下游问题。
9. **结论**：至少两个独立证据源一致；未验证的明确标注。

## 日志检索要点 [S-PTS-08]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

- 当前日志 + 子目录归档一起搜，不要只搜 `.log`。
- 用精确入口名/异常类名，不用泛化错误文案。
- `grep -a -n -H`：文本模式、行号、文件名。
- `-w` 全词匹配，避免 `sendMail` 命中 `sendOrderMail`。
- 压缩日志用 `zgrep` / `zcat` / `gunzip -c`。
- 文件名带空格要加引号；批量处理用 `-print0` + `xargs -0`。
- 大文件先解压一次到临时目录，避免反复解压。
- 中文乱码先确认编码，再 `iconv`；ASCII 的接口名/异常类名仍可搜。
- 容器环境用 `docker logs` / `kubectl logs`；systemd 用 `journalctl`。
- `printStackTrace()` 可能只写标准输出，不在应用日志文件里。

## 多入口/多端 [S-PTS-09]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

- 先沿路由/配置确认实际加载的组件，不要按文件名猜。
- 逐项比对入口、按钮显隐、请求 URL/参数/响应、字段绑定、校验、状态值、权限、后续消费者。
- 请求异常排查顺序：请求是否发出 → 拦截器 → API 封装 → 成功码判断 → 成功回调内部异常。
- 相同 API 名称/字段名称不能作为一致性证据，必须看实际请求与响应。

## 停止条件 [S-PTS-11]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。

> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

满足以下条件即可停止分析：

- 失败对象、成功标准、约束清楚；
- 关键结论有证据，或明确标为待确认；
- 已尝试反驳且替代解释被排除/标注；
- 方案、风险、剩余不确定性已呈现；
- 用户下一步选择明确，或证据缺口已说明。

不要为了“更深入”继续搜集不会改变结论的信息。
