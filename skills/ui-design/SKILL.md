# UI 设计

## 执行判据（本技能通用） [S-UID-01]

- **触发条件**：使用本技能处理其 description 所述任务时。
- **动作要求**：按本技能正文的步骤、约束和输出格式执行；涉及写文件、Git、外部发送、用户确认或其他状态变更时，先满足正文对应边界。
- **判断标准**：本技能要求的输入、步骤、输出/产物和检查项全部完成，并在回复或交付中给出可定位证据；未完成项标明阻断。
- **失败或例外处理**：前置条件不满足、信息缺失或用户未确认时暂停并说明缺失项，不得跳过、伪造或把未验证表述为完成。

先低成本敲定方向（ASCII 线框图对齐），再投入高保真原型（独立 HTML），全程不修改项目源码。两阶段分离避免方向没对齐就写整页 HTML 导致全盘返工。

## 先判断模式：轻量还是完整 [S-UID-02]

不是每个 UI 问题都需要全套两阶段。先按改动范围选模式：

| 模式 | 适用场景 | 做什么 |
|------|---------|--------|
| **轻量模式** | 局部微调：按钮大小、间距、颜色、对齐、字号 | 直接给诊断 + 具体建议（含数值），跳过线框图和原型 |
| **完整两阶段** | 区域重排、多方案对比、整页改版、新页面设计 | 走下面的第一阶段 + 第二阶段 |

判断标准：改动范围 ≤ 单个组件的样式属性（颜色、字号、间距、圆角、对齐）时走轻量模式；涉及区域重排、跨组件布局或多方案对比时走完整两阶段。改动同时命中两类特征，或从改动描述无法判断范围时，先向用户确认一个问题：「你是想微调，还是要重新排布局？」。

## 第一阶段：多方案设计 [S-UID-03]

**目标**：让用户在理解现有问题的基础上，从多个方案中做出知情选择。

1. **确认目标前端** - 一个项目可能有多个前端（主系统、微前端、移动端），各自的 UI 框架和令牌源不同，先确认改的是哪个。通用判断方法：看页面所在目录 + `package.json` 的依赖确定 UI 框架，再按框架找主题令牌源。以本项目（bp-lims）为例：

   | 目标前端 | 框架 | 令牌源 |
   |---------|------|--------|
   | hussar-front | Element UI 2.15 | Element UI 主题变量 + 项目全局 SCSS/Less |
   | eln-microapp | Element Plus | Element Plus 主题变量 + Vite 配置 |
   | hussar-mobile / hussar-mobile-wx | Vant / Element UI | Vant 主题变量 + 移动端样式 |

   换到其他项目时，按「页面目录 -> package.json 依赖 -> 框架主题变量位置」自行定位令牌源（Element UI/Plus 看 `theme-chalk` 覆盖和全局 SCSS；Ant Design 看 ConfigProvider token；Vant 看 `ConfigProvider` 主题变量）。无法从页面目录、package.json 依赖或框架文档确认令牌源位置时，向用户确认。令牌提取必须按目标前端切换，不能给 Vant 页面套 Element UI 的尺寸体系。

2. **提取现有设计令牌** - 从目标前端的样式定义中提取：
   - 主题色（primary / success / warning / danger）
   - 按钮尺寸（大/中/小的 padding、font-size、border-radius）
   - 输入框尺寸（height、padding、border-color）
   - 表格样式（header 背景色、行高、边框）
   - 间距体系（4/8/12/16/24/32px 的使用规律）
   - 字号体系（标题、正文、辅助文字的 font-size 和 font-weight）

3. **探索现有实现** - 读取目标页面的 Vue 组件、关联子组件、CSS 样式，理解当前 DOM 结构、数据流和交互逻辑
4. **诊断问题** - 用 3-5 条概述当前 UI 的核心问题（空间浪费、布局缺陷、交互割裂等）
5. **设计方案（2-3 个）** - 每个方案包含 ASCII 线框图（标注关键尺寸和区域）+ 文字说明方案特点 + 适用场景。线框图示例：

   ```text
   方案 A：单行密集查询区
   +----------------------------------------------------------+
   | 查询区  [输入] [输入] [下拉]      [查询] [重置] [导出]   |
   +----------------------------------------------------------+
   | 表格区  flex:1，占满剩余高度                              |
   | +------+------+--------+--------+------+               |
   | | 序号 | 字段A| 字段B  | 状态   | 操作 |               |
   | +------+------+--------+--------+------+               |
   | | 1    | ...  | ...    | ...    | ...  |               |
   | +------+------+--------+--------+------+               |
   |                                [分页]                   |
   +----------------------------------------------------------+
   ```

6. **方案对比表** - 维度包括：信息密度、切换成本、空间利用、视觉整洁度、实现复杂度、**风格一致性**。对比表示例：

   | 维度 | 方案 A（单行密集） | 方案 B（双行分组） |
   |------|------------------|------------------|
   | 信息密度 | 高 | 中 |
   | 空间利用 | 查询区省一行 | 查询区占两行 |
   | 实现复杂度 | 低 | 中 |
   | 风格一致性 | 与现有页面一致 | 引入新分组样式 |

7. **给出推荐** - 推荐理由必须包含三项：该方案解决的第一阶段诊断出的哪一条核心问题、与备选方案相比的关键取舍、以及与现有设计令牌的一致性结论；仅写「推荐方案 X」而无这三项时不合格
8. **等待用户选定方向**；例外：自主执行模式或用户要求直接产出时，按推荐方案继续，并在交付中标注「方向未经用户确认」

## 第二阶段：独立 HTML 原型 [S-UID-04]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

**目标**：基于选定方案生成可预览的独立原型，验证视觉效果。

- **从模板起步** - 复制 `assets/prototype-template.html` 作为起点，它已预接好 Element UI CDN + 设计令牌 CSS 变量占位 + 查询区/表格骨架。在模板上改，不要从零写。目标前端是 Element Plus 或 Vant 时，按模板文末 `切换前端` 注释替换 CDN、组件标签和挂载方式（Plus 用 `createApp` + `app.use`，Vant 改单列布局）
- **输出路径** - 原型存到 `docs/ui-prototypes/{页面名}-{日期}.html`（或用户指定路径）。不要放在 `src/` 下，避免被构建打包
- **CSS 变量必须来自系统** - 从第一阶段提取的设计令牌填入模板的 CSS 变量，不得凭感觉设值
- 原型包含真实数据模拟和完整的视觉样式
- 在不与项目代码耦合的前提下，原型的布局结构、组件层级和交互状态必须与第一阶段选定方案一致；颜色、字号、间距、组件尺寸必须来自第一阶段提取的设计令牌，不得引入新值
- **禁止**凭感觉设置颜色/字号--每个值必须能追溯到系统已有页面或主题变量

## 核心规则 [S-UID-05]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

1. **系统一致性优先** - 设计令牌（颜色、字号、间距、组件尺寸）必须复用现有系统已有的定义，不得随意引入新值。仅在系统确实无覆盖的场景下才自定义，并说明理由
2. 第一阶段只出方案，不动代码--ASCII 线框图 + 文字说明，不写任何 HTML/CSS
3. 第二阶段只出独立原型，不改项目文件--HTML 文件独立存放，不触碰 .vue/.js/.css
4. 方案对比表必须包含--不能只给一个方案，至少 2 个备选
5. 推荐必须有理由--要说明为什么适合当前场景

## 实现约束（原型落地规则） [S-UID-06]

> 触发条件：将原型方案落地到项目组件或样式时。

> 通用约束（scoped 样式、响应式验证、空间策略）见用户级规范 `~/.zcode/rules/frontend.md`。

1. **原型是设计稿不是代码模板** - 不得直接复制原型 HTML/CSS 到项目
2. **禁止照抄原型 CSS** - 原型常用 px 硬编码/全局选择器/`!important`，项目必须用 scoped + 设计变量
3. **保留组件行为** - 样式修改不得破坏弹窗开关、表单校验、表格排序筛选、vxe-table row-id 配置
4. **验证诚实** - 无法视觉验证时说明阻断原因，不得声称 UI 正确

### 系统一致性（硬约束，优先级最高） [S-UID-07.01]

### 核心要点 [S-UID-07.02]

> 触发条件：执行本节流程时。
> 动作要求：按本节步骤、约束和示例执行；涉及用户确认、写操作、外部调用或其他状态变更时先满足前置条件。
> 判断标准：本节要求的步骤、输出或检查项全部完成，并能定位到实际产物或证据；未完成项标明阻断。
> 失败或例外处理：前置条件不满足或信息缺失时暂停并说明缺失项，不得跳过或伪造结果。

- **两轮工作法** - 先出设计计划（令牌+线框图+标志性元素），自审是否为通用默认，修订后再构建
- **克制** - 一个页面一个视觉重点，其余安静。后台系统的重点是数据，不是装饰；想加的装饰元素先问「这个帮用户读数据了吗」，不帮就去掉
- **避免 AI 默认风格** - 渐变卡片、毛玻璃、过大留白、彩色阴影是几种「没想清楚就套」的默认。企业后台要的是信息密度和可扫读，不是视觉惊艳
- **文案从用户视角** - 平实语言、主动语态、错误只指引不道歉
- **首屏即论点** - 以最重要的数据或操作开场；字体、结构、动画都应有意识选择，不是默认
