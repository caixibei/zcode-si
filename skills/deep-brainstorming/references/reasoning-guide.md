# Sequence-Thinking 推理指南（深度脑暴专用）

本技能将 sequence-thinking 作为**核心推理引擎**，不是最后串联一下，而是贯穿整个推理过程——每轮处理一个推理阶段，支持回溯、修正和自我质疑。

## 与串联用法的区别

| 维度 | 串联用法 | 本技能的用法 |
|------|---------|-------------|
| 调用时机 | 所有节点确认后一次性调用 | 分 5 轮逐步调用 |
| 目的 | 把已确认节点排顺序 | 建立事实→验证假设→推理→质疑→综合 |
| 输入 | 已确认的路径节点 | Phase 1 的原始搜集结果 |
| 自我质疑 | 无 | Round 4 必须对每个结论尝试反驳 |
| 循环 | 无 | 发现信息缺口可回到搜集阶段补充 |

## 工具

优先调用会话中已注册的 sequential-thinking 类 MCP 工具（ZCode 环境下为 `mcp__sequentialthinking__sequentialthinking`；其他环境的工具名以实际注册为准，能力等价即可）。环境没有该 MCP 时，直接用文字分步推理，见文末「轮数弹性」的降级配合。

常用参数：
- `thought` — 当前推理步骤的内容
- `thoughtNumber` / `totalThoughts` — 进度；可随进展调高或调低总数
- `nextThoughtNeeded` — 在推理链稳定前保持 true
- `isRevision` / `revisesThought` — 当后续事实推翻先前结论时
- `branchFromThought` / `branchId` — 探索备选推理路径时
- `needsMoreThoughts` — 接近尾声但发现还需更多推理时

## 5 轮推理结构

> 下文示例以 Web 后端项目（额度校验、出库状态字段等）为背景，**仅为格式示范**--实际使用时替换为当前项目的表名、方法名、文件路径。示例教的是 thought 的组织方式，不是具体业务知识。

### Round 1: 建立事实基线

**目的**：从 Phase 1 的所有搜集结果中，提取确认的事实和待验证的假设。

**输入**：Phase 1 所有 agent 的 findings 汇总

**thought 内容要求**：
1. 逐条列出有代码/数据支撑的**确认事实**
2. 逐条列出仅有描述但无代码支撑的**假设**
3. 标注每条事实的来源（哪个 agent、哪个文件/SQL/URL）
4. 标注事实之间的关联（A 事实是否依赖 B 事实）

**输出标准**：
- 确认事实 ≥ 3 条（否则信息搜集不够，需要回到 Phase 1）
- 每条事实都有明确来源
- 假设清单完整，没有遗漏

**示例**：
```
thought: "事实基线建立：
确认事实：
1. [代码搜索] 出库申请状态字段在 bp_warehouse_outbound 表的 status 列，枚举值 0-5
   来源：BpWarehouseOutbound.java:45, WarehouseOutboundMapper.xml:12
2. [数据验证] 当前数据库中 status=3 的记录有 127 条
   来源：SELECT status, COUNT(*) FROM bp_warehouse_outbound GROUP BY status
3. [业务上下文] 额度校验公式：申请金额 > (accumulated + monthly_fixed + extra - used)
   来源：项目指令文件「额度管理」业务规则

假设：
1. 管理员直出库不走额度校验 — 有代码依据但未验证所有入口
2. extra_quota 每月1号清空 — 有文档但未找到定时任务代码

事实关联：事实1（状态枚举）→ 决定了哪些状态需要额度校验"
```

### Round 2: 假设验证

**目的**：对 Round 1 列出的每个假设，逐一验证。

**输入**：Round 1 的事实基线 + 假设清单

**thought 内容要求**：
1. 对每个假设，说明验证方法（查代码、查数据、查文档）
2. 标注验证结果：✅ 已验证 / ❌ 已推翻 / ⚠️ 待验证
3. 对已推翻的假设，说明推翻依据
4. 对待验证的假设，说明需要什么额外信息

**输出标准**：
- 所有假设都有验证结果
- 待验证假设 ≤ 2 条（否则需要回到 Phase 1 补充）
- 已推翻假设不影响后续推理链

**示例**：
```
thought: "假设验证：
1. 管理员直出库不走额度校验
   验证方法：Grep 搜索额度校验调用点
   结果：✅ 已验证 — OutboundService.java:128 的 checkQuota() 调用前有 role != ADMIN 判断
   来源：OutboundService.java:125-130

2. extra_quota 每月1号清空
   验证方法：Grep 搜索 extra_quota 的 UPDATE 语句
   结果：⚠️ 待验证 — 找到 QuotaResetJob.java 但未确认触发时间
   需要：读取 QuotaResetJob.java 的 @Scheduled 注解

3. used_quota 是累加写入
   验证方法：检查 Mapper XML 的 UPDATE 语句
   结果：❌ 已推翻 — 当前代码是 SET used_quota = #{amount}（覆盖），不是 used_quota = used_quota + #{amount}
   影响：这是一个确认的 Bug"
```

### Round 3: 逐步推理

**目的**：基于确认事实和已验证假设，建立推理链。

**输入**：Round 1 的确认事实 + Round 2 的已验证假设

**thought 内容要求**：
1. 每步推理必须标注：前提来源（哪个事实/假设）、推理逻辑、结论、不确定性
2. 步骤之间必须有因果关系（A 的结论是 B 的前提）
3. 不确定性高的步骤标记为 ⚠️
4. 如果推理链断裂（前提不充分），标记为 🔴

**输出标准**：
- 推理链 ≥ 3 步
- 每步都有前提→推理→结论的完整链路
- 不确定性标注完整

**示例**：
```
thought: "逐步推理：
Step 1: 用户提交出库申请
  前提：事实1（状态枚举 0-5）+ 事实3（额度校验公式）
  推理：申请进入 status=0（待审核），触发额度校验
  结论：待审核状态的申请需要通过额度校验
  不确定性：低 ✅

Step 2: 额度校验失败场景
  前提：Step 1 + 假设1已验证（管理员跳过）+ 事实2（127条status=3记录）
  推理：非管理员用户申请金额超过剩余额度时，校验失败
  结论：校验失败的申请不会进入后续流程
  不确定性：低 ✅

Step 3: used_quota 累加问题
  前提：Step 2 + 假设3已推翻（覆盖写入）
  推理：如果 used_quota 是覆盖而非累加，多次申请后额度计算会出错
  结论：额度校验结果不可靠，可能导致超额出库
  不确定性：⚠️ 需要确认是否有其他机制补偿"
```

### Round 4: 自我质疑

**目的**：对 Round 3 的每个结论尝试反驳。

**输入**：Round 3 的推理链

**thought 内容要求**：
1. 对每个结论，提出至少一个反驳论点
2. 评估反驳是否成立
3. 如果反驳成立，说明需要如何修正结论
4. 如果反驳不成立，说明为什么结论经得住质疑

**输出标准**：
- 每个重要结论都有反驳尝试
- 反驳成立的结论标记为需要修正
- 修正后的结论重新评估置信度

**示例**：
```
thought: "自我质疑：

Step 1 结论：待审核状态的申请需要通过额度校验
  反驳：是否有批量导入场景跳过额度校验？
  验证：Grep 搜索 import/batch 相关入口
  结果：反驳不成立 — 批量导入走同一个 Service 方法
  置信度：维持 0.95

Step 3 结论：额度校验结果不可靠，可能导致超额出库
  反驳：是否有审批环节作为二次校验？
  验证：检查审批流程代码
  结果：反驳部分成立 — 审批环节会重新查询额度，但用的是同一个可能被覆盖的 used_quota
  修正：结论修正为「审批环节的二次校验也不能完全防止超额」
  置信度：从 0.7 降到 0.6
```

### Round 5: 综合判断

**目的**：基于经质疑后的推理链，给出最终结论。

**输入**：Round 4 经质疑和修正后的推理链

**thought 内容要求**：
1. 最终结论（简洁、可执行）
2. 置信度（0-1，基于事实支撑度和质疑通过率）
3. 剩余不确定性（诚实报告，不刻意淡化）
4. 建议的下一步行动

**输出标准**：
- 结论 ≤ 3 条（聚焦核心问题）
- 每条结论有明确的置信度
- 剩余不确定性列出，标注是否影响结论可信度
- 下一步行动具体可执行

**示例**：
```
thought: "综合判断：

最终结论：
1. used_quota 覆盖写入是确认的 Bug（置信度: 0.99）
   依据：代码明确是 SET used_quota = #{amount}，不是累加
   影响：多次出库申请后额度计算错误，可能导致超额出库

2. 管理员直出库不走额度校验是设计如此（置信度: 0.95）
   依据：代码有明确的 role 判断

3. 审批环节的二次校验存在漏洞（置信度: 0.6）
   依据：审批查询同一个可能被覆盖的字段

剩余不确定性：
- 审批环节是否有其他补偿机制？（影响结论3的可信度）
- 生产环境是否已出现超额出库？（需要数据验证）

建议下一步：
1. 修复 used_quota 累加 Bug（高优先级）
2. 验证审批环节是否有其他补偿机制
3. 检查生产数据是否有超额出库记录"
```

## 轮数弹性

5 轮是完整结构，不是教条。问题复杂度不同，轮次可伸缩，但有一条不可省的底线。

**不可省的两轮**：
- **Round 1（事实-假设区分）** - 这是整个推理的地基。跳过它，后面的验证、推理、质疑都建立在未区分的事实和假设上，结论不可信
- **Round 4（自我质疑）** - 这是防止过早收敛的最后一道闸。跳过它，推理链再长也只是单向论证，没人反驳

**可合并的轮次**：
- 简单问题（单一根因、少分支）：Round 2（假设验证）可合进 Round 3（逐步推理）--边推理边验证假设，一轮搞定
- Round 3 和 Round 5 不建议合并：Round 5 的综合判断需要 Round 4 质疑完成后才能做，合并会让质疑结果无处安放

**判断标准**：
- 结论要写进分析报告、驱动决策 -> Round 1 + Round 4 必须独立做，不可省、不可合并
- 探索性推理、结论仅供讨论 -> 可压缩，但 Round 1 和 Round 4 仍要用文字走一遍

**降级配合**：sequential-thinking 类 MCP 不可用时，用文字分步写出每轮 thought（每轮按上文各轮的 thought 内容要求与输出标准组织），弹性规则不变。

## 循环回到搜集阶段

当 Round 2 或 Round 4 发现信息缺口时：

1. 明确列出需要补充的信息（具体到表名、函数名、文件路径）
2. 回到 Phase 1，只派出缺口维度的 agent
3. 补充后重新进入 Round 2 或 Round 4
4. 最多 2 轮循环

**循环判断标准**：
- 关键假设无法验证 → 必须循环
- 推理链某步置信度 < 0.6 → 建议循环
- 自我质疑发现反驳成立且需要额外信息 → 建议循环
- 仅是「不够完美」的不确定性 → 不循环，标记为待确认

## 交付规则

**禁止**把 sequence-thinking 的原始倾倒当作主回答。

用人话协作语气复述，例如：

> 我从 5 个维度搜集了信息，核心发现是：
> 1. used_quota 字段当前是覆盖写入，不是累加 — 这是一个确认的 Bug
> 2. 管理员出库不走额度校验 — 这是设计如此
>
> 推理链经过自我质疑后，主要结论的置信度较高（0.95+），
> 但审批环节的二次校验机制还需要进一步确认（置信度 0.6）。
>
> 这样理解对吗？

然后等认可，再写分析报告文档。

## 反模式

| 反模式 | 正确做法 |
|--------|----------|
| 一次性调用 sequence-thinking 串联所有结论 | 分 5 轮逐步调用，每轮一个推理阶段 |
| 跳过自我质疑直接输出结论 | Round 4 必须对每个结论尝试反驳 |
| 把假设当事实写进推理链 | Round 1 严格区分事实和假设 |
| 发现信息缺口但假装没看到 | 回到 Phase 1 补充缺口维度 |
| 把工具思考原文贴给用户 | 用人话复述推理链和结论 |
| 不确定性刻意淡化 | 诚实报告剩余不确定性 |
| 推理链断裂但强行继续 | 标记为 🔴 并说明断裂原因 |
