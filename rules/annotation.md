# 业务注释要求（绝对强制）

适用于 Java、MyBatis XML、SQL 及 Vue/JavaScript 业务逻辑的新增、修改、删除和重构。

**触发时机**：每次 Edit/Write 修改业务代码前自动执行，与代码变更在同一次 Edit 中一起写入。

## 核心原则 [R-ANN-01]

> 触发条件：新增、修改、删除或重构 Java、MyBatis XML、SQL、Vue/JavaScript 业务代码前。
> 动作要求：先判断能否用代码表达；不能表达的业务语义按业务段落补注释；修改任意一行必须审查全方法。
> 判断标准：注释解释“为什么存在、数据从哪来、处理后到哪里去”；无逐行翻译、无自证性注释、无未确认 TODO。
> 失败或例外处理：业务语义无法从代码或证据确定时标记待确认并暂停；不得用 TODO 代替业务确认。

- **能由代码清楚表达的技术动作，不写重复注释**。业务数据来源、关联依据、计算口径、分支影响和结果去向不属于技术动作，即使变量名或方法名清晰也必须在对应业务段落说明；写注释前仍应评估能否通过重命名或提取方法降低实现复杂度。
- 注释解释"为什么存在、数据从哪来、处理后到哪里去"，**不翻译代码**。
- 注释只说明代码本身无法表达的约束；禁止陈述下一行代码做什么、解释本次改动为什么正确，或向审查者叙述变更过程。
- 方法级 Javadoc 负责方法整体契约，不能替代方法体内按业务时间线划分的段落注释；触发入口、参与范围、局部数据来源、关联方式、转换口径、分支影响、外部交互和结果去向必须在对应代码段前说明。
- 方法体注释以连续的业务逻辑段落为单位，同一业务目的的相邻语句可由一条注释覆盖；业务目的、数据来源、参与范围、处理阶段或结果去向变化时必须另起段落。禁止逐行翻译代码，也禁止因变量名或被调方法名清晰而省略无法由代码表达的业务语义。
- 修改方法任意一行，必须审查该方法全部业务逻辑段落；不得出现两个及以上连续业务目的、数据来源、处理阶段或结果去向已经变化，但中间没有对应业务段落注释的断层。
- 业务正确性优先。历史方法复杂时，不为满足注释或分层要求强制拆分。
- TODO 只能标记不阻断当前行为的待确认信息，不能作为改变业务语义的依据。涉及权限、金额、状态流转、工作流、数据归属或外部字段契约时，必须先向用户确认，不得以 TODO 代替确认后继续实施。TODO 中的相对日期（如“9月底”）必须转为绝对日期（如“2026-09-30”）。
- 清单必须基于已读取代码，**禁止先勾选后补审查**。

编辑前检查清单的强制输出格式见 `~/.zcode/AGENTS.md`「编辑前必须输出」，分档详细清单（A/B/C 档）见本文件末尾「编辑前审查清单（A/B/C 档）」。编辑时审查流程、编辑后复查（DoD）见 `~/.zcode/AGENTS.md`「编辑前硬规则（强制执行）」。

## 跨边界数据模型字段注释 [R-ANN-02]

> 触发条件：新增或修改跨模块、导出、外部接口、同步中间表使用的 Entity、DTO、VO、MyBatis 投影或导出模型时。
> 动作要求：逐字段审查数据契约；对外语义不能由字段名/类型/注解唯一表达时写字段级 Javadoc。
> 判断标准：适用字段说明来源/去向/口径/空值/时间语义/历史兼容；仅内部使用字段在审查计划中说明排除理由。
> 失败或例外处理：来源或口径无法确认时标记待确认，不得猜表名或编造单位。

新增或修改跨模块、导出、外部接口、同步中间表使用的 Entity、DTO、VO、MyBatis 查询投影或导出模型时，必须逐字段审查数据契约。

- 新建模型：所有字段均需审查；修改既有模型：审查本次新增、修改字段，以及与其共同构成同一外部契约的关联字段。
- 对外语义不能由字段名、类型或 `@TableField` 唯一表达的字段，必须在同次修改写字段级 Javadoc，至少说明适用项：来源表/字段或计算来源、输出对象和用途、金额/数量/单位/日期/编码/状态口径、`NULL` 或默认值含义、历史兼容约束。
- 来源业务时间与同步、导出或生成时间并存时，必须明确两者的业务区别，不得仅写“创建时间”或“同步时间”。
- 仅在当前类内部使用且不存在外部数据契约的字段，可不补字段注释；审查计划中须说明其不属于跨边界模型的理由。

`@TableId`、`@TableField` 与英文命名只能表达技术映射，不能替代来源、去向、空值与口径说明。

## 公共 API 与兼容入口注释 [R-ANN-03]

> 触发条件：新增、修改或保留公共工具类、公共 Java 类、跨页面复用 .js 模块的公开方法时。
> 动作要求：审查完整公开方法集合；新增/重载/覆写/兼容入口按契约要求补 Javadoc/JSDoc 和示例。
> 判断标准：业务目的、入参/结果、前置条件、副作用、异常语义可定位；兼容入口有 @Deprecated/迁移方式；示例只展示调用约束。
> 失败或例外处理：无法确认调用方或兼容语义时保留原入口并标记待确认，不得因仓库搜不到调用方就删除。

公共工具类、公共 Java 类及跨页面复用的 `.js` 模块，新增、修改或保留兼容方法时，必须审查该 API 的完整公开方法集合，并在同次编辑补齐契约注释。

- 新增公开方法：说明业务目的、入参与结果的业务含义、调用前置条件、关键副作用及异常语义；存在非直觉调用顺序或组合方式时，提供最小使用示例。
- 兼容保留的方法：使用 `@Deprecated`（Java Javadoc）或 `@deprecated`（JSDoc）标记替代入口、保留原因和迁移方式；不得只因当前仓库搜索不到调用方就删除或改变完成、异常语义。
- 重载或覆写方法：说明相对同名方法或父类契约的适用场景、参数差异、实际业务意义和最小调用示例；不得仅复述“重载”或“覆写”。
- 示例只展示调用约束或业务场景，不复制完整实现；简单、单一用途且代码自解释的私有方法不强制添加示例。判定为“简单”的充分条件（同时满足以下 3 项即可不添加示例）：无分支或仅单分支、入参与返回类型可唯一确定行为、方法名能完整表达业务语义；不满足任一项时，须按公共 API 要求补齐最小使用示例。

## 方法体业务段落注释（强制） [R-ANN-04]

> 触发条件：方法体存在触发入口、参与范围、数据取得、转换、分支、临时对象、外部交互、异常或最终写入等业务段落时。
> 动作要求：按业务时间线逐段审查；存在任一项时在对应代码段前写业务注释，不能以类注释/方法 Javadoc/变量名代替。
> 判断标准：9 类段落逐项判断适用性；适用段落说明来源、目的、关键分支、结果去向；无连续业务段落断层；无逐行翻译。
> 失败或例外处理：业务目的或结果去向无法确认时标记待确认并暂停；不得用“获取数据/处理结果”等无业务信息表述替代。

方法级 Javadoc 只描述方法整体职责和契约。方法体必须按实际业务操作的时间线审查下列段落；存在任一项时，须在对应代码段前写业务注释，不能以类注释、方法 Javadoc、变量名或被调方法名代替：

1. **触发入口与上下文准备**：说明用户操作、Controller 接口、定时任务、事件监听器或上游方法何时进入当前逻辑；入参、登录上下文、缓存或临时状态来自哪里，供后续哪个阶段使用。
2. **参与人、角色、组织与权限范围**：说明哪些业务参与者被纳入或排除、角色/组织条件代表什么、筛选结果影响哪些数据、按钮、接收人或后续权限判断。
3. **数据取得与关联装配**：说明当前数据来自哪个前置查询、入参或上下文，以什么业务键关联，缺失时如何处理，结果供哪个后续步骤使用。
4. **转换、聚合、排序、去重与计算**：说明输入口径、单位、边界、舍入、顺序或去重规则，以及转换结果写入、返回或传递到哪里；代码只能体现公式而不能体现业务理由时，必须说明理由。
5. **状态、权限、金额与时间分支**：说明进入条件代表的业务场景、边界是否包含、分支对持久化、流程、页面状态或对外输出的影响。
6. **临时字段、正文、附件与跨步骤对象装配**：说明借用字段、中间对象、通知正文或附件的来源、生命周期和使用方，以及是否写回持久层，防止维护者误当作实体真实语义。
7. **外部系统调用与副作用**：说明调用的外部系统或组件、业务目的、关键输入/输出、发送或写入对象，以及失败是否允许重试、降级或继续后续步骤。
8. **异常隔离、降级与失败去向**：说明失败影响当前记录还是整批任务、是否继续处理、事务或状态是否保持原状，以及为什么允许该策略；异常转换或吞掉异常时必须写清原始失败如何暴露。
9. **最终写入、响应与后续调用**：说明本方法最终修改哪些持久化状态、返回给哪个页面/接口、触发哪个流程或通知；空结果、零影响行和部分成功如何体现给调用方。

同一业务目的下连续的数据读取、转换和结果装配可以由一条段落注释覆盖；业务目的、数据来源、参与范围、处理阶段或结果去向变化时必须另起注释。集合初始化、判空、日志和直接委托若不承载额外业务语义，可由所属业务段落统一覆盖，不强制单独注释。长历史方法允许使用“第一步：获取基础信息”“第二步：组装接收范围”等有明确业务名称的阶段标题帮助呈现时间线，但阶段标题不能代替阶段内的数据来源、业务目的、关键分支、外部交互和结果去向说明。禁止逐行翻译语句，也禁止使用“获取数据”“计算数值”“处理结果”等没有业务信息的表述。

### 方法体正确示例 [R-ANN-04.01]

```java
// 主记录来自本次批量查询；关联配置与历史记录由前置查询按业务主键装配。
// 主记录或必需配置缺失时跳过当前项，空历史集合按无历史记录处理，装配结果供本轮规则计算。
BusinessRecord record = recordById.get(item.getBusinessId());
RuleConfig rule = ruleByType.get(record.getType());
List<HistoryRecord> histories = historiesByBusinessId.getOrDefault(
        record.getId(), Collections.emptyList());

// 原始值按配置的单位、精度和历史累计口径转换；中间结果仅供当前判定与响应装配，不覆盖持久化字段。
BigDecimal normalizedValue = ruleCalculator.normalize(item.getSourceValue(), rule);
BigDecimal availableValue = ruleCalculator.calculateAvailable(
        normalizedValue, histories, calculateTime);

// 只有同时满足状态与阈值条件的记录进入后续处理集合；未命中记录保持原状态且不触发后续副作用。
if (eligibilityPolicy.isEligible(record.getState(), availableValue)) {
    eligibleResults.add(buildResult(record, availableValue));
}
```

## Javadoc 格式规范（可读性） [R-ANN-05]

> 触发条件：编写或修改 Java 方法/类 Javadoc 时。
> 动作要求：按 Why > What > How 组织；按内容类型选择 <p>/<ul>/<ol>/{@code}/{@link}/<b>；按块标签 CRUD 预查。
> 判断标准：摘要句完整；独立业务维度显式闭合；3 项以上枚举用列表；块标签合法、语义真实、顺序符合；@author 规则符合。
> 失败或例外处理：标签语义无法核实时保留原值并标注待确认；不得猜版本、删除历史作者或把 @date 机械转成 @since。

遵循 Java 官方 Javadoc 规范 + Spring 风格，方法级注释必须使用 `/** */` 格式。

### 核心理念：Why > What > How [R-ANN-05.01]

> 判断标准：先说明设计意图/权衡，再说明是什么，最后说明实现；代码已能表达时不写重复注释。

先解释"为什么这么做"（设计意图、权衡），再描述"这是什么"，最后才是"怎么实现"。实现细节应让代码自解释：当变量名、方法名或类型已能唯一表达行为时，不写重复注释；仅当代码无法表达业务语义（数据来源、关联依据、计算口径、分支影响、结果去向）时才写注释。

### 注释金字塔（按层级侧重） [R-ANN-05.02]

> 触发条件：编写类/方法 Javadoc 时。

> 判断标准：公开接口/实现类/私有复杂逻辑分别覆盖 API 契约/设计选择/业务规则；层级与内容匹配。

| 层级 | 注释重点 | 说明 |
|------|---------|------|
| 公开接口 | API 契约 | 前置条件、后置条件、异常、线程安全性 |
| 实现类 | 设计选择 | 用了什么策略/数据结构？为什么这样选？ |
| 私有复杂逻辑 | 业务规则 | 无法重构得更清晰时，解释"为什么"优先于"做了什么" |

### HTML 标签选择规则 [R-ANN-05.03]

> 触发条件：Javadoc 正文需要选择 HTML 标签时。

> 判断标准：按内容类型选择标签；3 项以上枚举必须用 <ul>/<li>；可解析链接用 {@link}；代码标识符用 {@code}；关键术语用 <b>；每段显式闭合。

**决策流程**：先判断内容类型，再选择对应标签。

| 内容类型 | 应选标签 | 说明 |
|----------|---------|------|
| 单句描述、独立业务维度 | `<p>...</p>` | 每段显式闭合；不得依赖源码换行产生渲染换行 |
| **3 项以上枚举** | **`<ul>/<li>`** | **步骤、规则、子功能列表——必须用列表，禁止硬塞进 `<p>`** |
| 有序步骤、优先级排序 | `<ol>/<li>` | 有明确先后顺序的流程 |
| 表名、字段名、方法名 | `{@code}` | 与正文视觉区分，不依赖引号 |
| 可访问且可唯一解析的类型、成员或字段 | `{@link}` | Javadoc 工具可生成超链接；无法解析时改用 `{@code}` |
| **关键术语强调** | **`<b>`** | **业务概念首次出现时加粗，与 `{@code}` 区分——`{@code}` 用于代码标识符，`<b>` 用于自然语言术语** |
| 正文内强调 | `<strong>` | 与 `<b>` 等效，用于段落内强调 |

**关键决策规则**：

```
内容是可访问且可唯一解析的类型、成员或字段？ -> {@link}
内容是其他代码标识符（表名/字段名/方法名）？ -> {@code}
内容是枚举列表（≥3 项）？               -> <ul>/<li>
内容是有序流程？                         -> <ol>/<li>
内容是自然语言关键术语？                 -> <b>
以上都不是？                             -> <p> 段落内联
```

### Javadoc 段落渲染 [R-ANN-05.04]

> 触发条件：编写多段 Javadoc 时。

> 判断标准：每个独立业务维度使用显式闭合 <p>；需要视觉分隔时用 <p>/<li>；3 项以上并列用 <ul>/<li>。

- 每个独立业务维度使用显式闭合的 `<p>...</p>`；包括触发入口、参与范围、业务目的、数据来源、条件与可见范围、转换口径、外部交互、结果去向、空结果处理和性能意图。
- Documentation 按 HTML 渲染，源码换行会折叠为空格；需要视觉分隔时使用 `<p>` 或 `<li>`，不得只换行。
- 同一段存在 3 项以上并列规则时使用 `<ul><li>...</li></ul>`，每项独占一个 `<li>`。

### Javadoc 块标签预查与 CRUD [R-ANN-05.05]

> 判断标准：完整读取并盘点；合法性/新增/更新/删除/保留/顺序/语义禁止逐项有结论；@author 规则符合。

编辑任何 Java 文件前，必须完整读取目标文件并盘点现有 Javadoc 块标签；不得只检查准备修改的注释片段。文件超过大型文件阈值时允许分块 Read，但分块集合必须覆盖文件首尾、全部顶层类型、全部 Javadoc 块及所有公开方法签名；完成后才算“完整读取”。

- **合法性**：以当前项目 JDK 的标准 doclet 标签为准；常见标准块标签包括 `@author`、`@version`、`@since`、`@param`、`@return`、`@throws`/`@exception`、`@see`、`@deprecated` 和 `@serial*`。自定义标签仅在项目规则或 Javadoc 配置明确登记时有效；登记证据为目标项目 `pom.xml` 的 Javadoc 插件配置或项目级 `AGENTS.md` 登记清单。未登记的 `@date`、`@Description` 等视为无效。
- **Create**：新增或本次编辑涉及的 Java 顶层 `class`、`interface`、`enum`、`@interface`，以及项目 JDK 支持时的 `record`，其类级 Javadoc 必须至少包含一个 `@author`。作者取值优先级为：用户本次指定 → 项目明确约定 → 用户级默认值 `Alden`；已有合法作者时不追加 `Alden`。其他标签仅在语义真实、当前不存在且信息来源可靠时新增。
- **Update**：已有标签与当前签名或事实不一致时更新；已有标准标签的版本或异常语义暂时无法核实时，保留原值并在审查计划标注“待确认”，不得猜测、删除或另行新增。已有合法 `@author` 无须重新核实身份，不得擅自替换。
- **Delete**：删除未登记的非标准标签、与当前签名不对应的 `@param`/`@return`/`@throws`、内容为空的标签及完全重复标签。
- **保留**：保留仍然有效的历史标签；不同作者的多个 `@author` 必须全部保留，仅对标签名和内容去除首尾空白后逐字一致的作者标签去重。
- **顺序**：类级标签统一为 `@author` → `@since` → `@version`；方法级 `@param` 按参数声明顺序排列，随后为 `@return`、`@throws`、`@see`、`@deprecated`。
- **语义禁止**：`@date` 不能机械转换为 `@since`；只有存在真实发行版本依据时才能新增或更新 `@since`。

### 结构模板 [R-ANN-05.06]

#### 类级 Javadoc

```java
/**
 * 类的业务职责一句话概括（以句号结尾）。
 *
 * <p>涵盖以下能力：</p>
 * <ul>
 *   <li>能力一：简要说明</li>
 *   <li>能力二：简要说明</li>
 *   <li>能力三：简要说明</li>
 * </ul>
 *
 * <p>关键约束或设计说明。</p>
 *
 * @author 已有合法作者；新增顶层类型且无其他已确认作者时使用 Alden
 * @since 已核实的引入版本；未知时省略
 * @version 已核实的当前版本；可选
 */
```

#### 方法级 Javadoc

> 判断标准：方法级 Javadoc 包含摘要句、详细描述、数据来源、结果去向；按结构模板输出。

```java
/**
 * 摘要句：一句话说明方法的业务功能（以句号结尾）。
 *
 * <p>详细描述：补充业务背景、计算逻辑、数据流转等。可使用 {@code 代码片段} 或 {@link 类名} 等内联标签。</p>
 *
 * <p>数据来源：业务主记录、关联配置与调用上下文；前置批量查询后按业务主键关联装配。</p>
 * <p>结果去向：转换结果用于后续条件判断和响应装配；必需数据缺失时按已确认契约返回、跳过或降级。</p>
 */
```

> **何时用 `<ul>` 替代 `<p>`**：当「详细描述」或「业务规则」中包含 **3 项以上并列内容**时，必须使用 `<ul>/<li>` 列表。
> 2 项以内且构成完整句子时，用 `<p>` 内联即可。

### Javadoc 规则 [R-ANN-05.07]

1. **摘要句**：第一句话是摘要，简洁完整地说明业务功能，以句号结尾。Javadoc 工具会提取到概览中。
2. **段落分隔**：每个独立业务维度使用显式闭合的 `<p>...</p>`；空行只分隔源码，不产生渲染换行。
3. **列表标记**：3 项以上枚举内容使用 `<ul>/<li>`，有序步骤使用 `<ol>/<li>`。
4. **代码标记**：表名、字段名、方法名用 `{@code}` 包裹，与正文区分。
5. **链接引用**：仅对当前上下文可访问且能唯一解析的类型、成员或字段使用 `{@link}`；重载方法须写明参数签名（如 `{@link BeanUtils#copyProperties(Object, Object)}`），无法解析或访问受限时改用 `{@code}`，不得为链接报错调整业务代码可见性。
6. **关键术语**：业务概念首次出现时用 `<b>` 加粗强调。
7. **块标签**：API 方法使用 `@param`、`@return`、`@throws`；业务方法可省略。
8. **行内注释**：按文件语法编写，Java 使用 `//` 或 `/** */`，MyBatis XML 使用 `<!-- -->`，SQL 使用 `--` 或 `/* ... */`，Vue / JavaScript 使用 `//` 或 `/** */`；内容标准见下方「业务注释检查清单」与「逻辑段落清单」。
9. **作者标注**：`@author` 只允许写在 Java 顶层类型的类级 Javadoc 中。新增或本次编辑涉及的顶层 `class`、`interface`、`enum`、`@interface`，以及项目 JDK 支持时的 `record`，类级 Javadoc 不能缺少 `@author`：优先使用用户本次指定或项目明确约定的作者；没有其他已确认作者时使用用户级默认值 `Alden`。已有一个或多个合法作者时不追加 `Alden`，不同作者全部保留，仅删除去除首尾空白后内容完全相同的重复项；不得擅自替换历史作者。
10. **示例稳定性**：全局规则示例不得固化项目专属表名、角色 ID、状态码、字段名或接收对象；应使用通用业务术语表达来源、口径和结果去向，具体契约留在项目规则或业务代码中。

## MyBatis XML SQL 注释规范 [R-ANN-06]

> 触发条件：新增或修改 MyBatis XML 的 select/insert/update/delete 语句时。
> 动作要求：使用 <!-- --> 注释；覆盖数据库调用 6 要素；与 Java Mapper 方法 Javadoc 互补。
> 判断标准：操作类型、数据来源、业务目的、条件与可见范围、结果/影响行用途、空结果/零影响行处理、执行时机均可定位。
> 失败或例外处理：表名或条件语义无法确认时写可核实的数据域并标记待确认，不得猜表名。

MyBatis XML 中的 `<select>`、`<insert>`、`<update>`、`<delete>` 语句必须使用 `<!-- -->` 注释，注释内容需覆盖「数据库调用注释的 6 个要素」。

### 注释结构模板 [R-ANN-06.01]

> 判断标准：模板字段齐全；模板不得替代具体业务语义。

```xml
<!--
    操作类型 + 简要说明。

    数据来源：涉及的表、关联关系
    业务目的：为什么需要这个操作，支撑业务时间线的哪个阶段
    条件与可见范围：WHERE 条件的业务含义
    结果或影响行用途：查询结果或写入结果的去向
    空结果或零影响行处理：空结果时的业务行为
    执行时机：何时调用（每次同步、首次同步、空候选也执行等）
-->
<select id="..." resultType="...">
    ...
</select>
```

### 与 Java 方法注释的关系 [R-ANN-06.02]

> 触发条件：编写 MyBatis Mapper Javadoc 或 XML 注释时。

> 判断标准：Java Mapper Javadoc 说明契约；XML 注释说明实现；两者互补且均存在。

- Java Mapper 接口的方法 Javadoc 负责**契约说明**（入参、返回值、异常）
- XML SQL 注释负责**实现说明**（数据来源、条件、执行时机）
- 两者互补，不得互相替代

## 新增文件注释门槛 [R-ANN-07]

> 触发条件：新增 Entity、Mapper、XML 或其他业务文件时。
> 动作要求：先读取同目录已有文件的最高注释水平作为基准，再补齐新增文件注释。
> 判断标准：新增文件注释详细程度不低于同目录最高基准；新增方法不低于同文件其他方法基准。
> 失败或例外处理：同目录无基准时说明参照文件/规则；不得以“新增文件”为由降低标准。

新增文件（Entity、Mapper、XML）的注释标准**不得低于**同目录下已有文件的最高注释水平：

- 新增 Mapper XML 时，先读取同目录其他 XML 的注释详细程度作为基准
- 新增方法时，先读取同文件其他方法的 Javadoc 详细程度作为基准
- 低于基准时必须补全，不得以"新增文件"为由降低标准

### Javadoc 正确示例 [R-ANN-07.01]

## 注释内容维度（逐项审查全部适用项） [R-ANN-08]

> 触发条件：审查方法级 Javadoc 或方法体业务段落时。
> 动作要求：对 9 项维度逐项判断适用性；适用项在 Javadoc 或对应段落覆盖。
> 判断标准：9 项均有“适用/不适用”结论；适用项可定位到具体注释；不得按“任选 N 项”达标。
> 失败或例外处理：无法判断适用性时标记待确认并暂停；不得用已有两个维度替代其余实际业务语义。

> 三个清单的分工：本清单（9 项）定义 Javadoc 与段落注释必须覆盖的信息维度；「方法体业务段落注释」（9 项）定义方法体内段落的划分方式；「逻辑段落清单」（20 项，其中 16–20 为前端专属）是按业务时间线枚举的完整段落清单，供审查计划分段使用。三者互补，不互相替代、不因另一清单存在而省略。

以下维度不是计数清单（不得按“任选其中 N 项即达标”执行）。每个受影响方法都必须逐项判断是否适用；适用项必须在方法级 Javadoc 或对应方法体业务段落中覆盖，不适用项可省略，但不能用已有两个维度替代其余实际存在的业务语义。

1. **触发入口与业务目的**：谁在什么操作、请求、事件或任务中进入该逻辑；解决什么需求或防止什么业务错误？
2. **参与范围与权限**：哪些角色、组织、用户或数据被纳入/排除，筛选结果影响什么？
3. **数据流转**：数据从哪来，按什么业务键关联，经过什么转换，写到哪里或返回给谁？
4. **转换与内容装配**：计算、聚合、排序、去重、正文、附件或临时对象采用什么口径，结果供谁使用？
5. **外部交互**：调用什么系统或组件，目的、关键输入输出、失败策略和副作用是什么？
6. **持久层调用**：查询/写入什么数据，条件与可见范围代表什么，结果或影响行用于哪里，空结果或零影响行如何处理？
7. **分支场景**：什么业务场景进入该路径，边界是否包含，持久化、流程、页面或通知结果有什么差异？
8. **异常与降级**：失败影响当前记录还是整批处理，是否继续、重试或保持原状态，异常如何反馈？
9. **最终结果与风险约束**：最终写入、响应或后续调用是什么；为什么要保留顺序、去重、恢复字段、隐藏敏感值或避免 N+1？

## 数据库调用注释的 6 个要素 [R-ANN-09]

> 触发条件：涉及 Mapper、DAO、Service 持久层方法或 MyBatis SQL 的每次查询/写入时。
> 动作要求：按 6 要素逐项说明，并串清“读取 → 转换/装配 → 写入或后续调用”的数据流。
> 判断标准：6 要素均可定位；空结果/零影响行处理明确；性能意图有依据；数据流连续。
> 失败或例外处理：表名或条件无法确认时写可核实数据域并标记待确认，不得猜表名或机械编造优化理由。

涉及 Mapper、DAO、Service 持久层方法、`getById`、`list`、`page`、`select*`、`insert*`、`update*`、`delete*` 或 MyBatis SQL 时，每一次查询或写入都必须逐项说明：

1. **数据来源/写入目标**：业务实体或表、关键字段；无法从当前代码确认具体表时，写可核实的 Mapper/Service 数据域，不得猜表名。
2. **业务目的**：为什么需要这次读取或写入，它支撑当前业务时间线的哪个阶段。
3. **条件与可见范围**：ID、状态、组织、项目编码、时间范围和权限过滤分别代表什么；写入条件如何限制目标记录。
4. **结果或影响行用途**：查询结果用于哪个 Map、转换、分支、响应字段或后续调用；写入结果或影响行数用于何种成功/冲突判断。
5. **空结果或零影响行处理**：跳过、返回空、报错、降级、保持原状态还是按并发冲突处理。
6. **性能意图**：调用处于循环、批量、高频或分页装配链路时，说明批量查询、分组回填、短路空集合或避免 N+1 的意图；确属单次低频调用时可明确“不在循环内，无批量访问风险”，不得机械编造优化理由。

数据库注释不能停在查询或写入动作本身；所在业务段落还必须串清“读取 → 转换/装配 → 写入或后续调用”的完整数据流。一次注释可覆盖同一业务目的下相邻且数据流连续的多次调用，但每个调用的来源/目标、条件、空值语义和结果去向仍须可辨认。

## 业务注释分类与规范 [R-ANN-10]

> 触发条件：编写业务规则、魔数、复杂算法、TODO 或异常处理注释时。
> 动作要求：按类型说明业务知识、来源、边界、责任人和失败语义；TODO 写清谁/何时/条件/后果并使用绝对日期。
> 判断标准：注释包含代码无法表达的“为什么/从哪来/到哪去”；魔数有来源；TODO 可追踪；异常吞掉/转换有原因。
> 失败或例外处理：业务规则来源缺失时标记待确认；不得用 TODO 代替权限/金额/状态/工作流/数据归属确认。

文档注释（Javadoc）面向 API 使用者，业务代码注释（`//`）面向未来维护这段代码的人。目标读者不同，规范也不同。

### 1. 业务规则与决策——最重要的注释 [R-ANN-10.01]

> 判断标准：业务规则注释关联需求/会议/事故记录；注释说明业务知识而非代码动作。

记录隐藏在代码背后的业务知识。当代码背后有需求文档、会议决议、线上事故修复记录时，必须用注释关联。

### 2. 魔数与常量解释 [R-ANN-10.02]

> 触发条件：代码出现魔数、阈值或固定延迟时。

> 判断标准：每个魔数/阈值注释来源和原因；示例中的 3000ms 必须解释业务延迟。

```java
// ❌ 魔数无解释
Thread.sleep(3000);

// ✅ 解释业务含义
// 支付回调后，银行流水有 3s 延迟，必须等待再查询
Thread.sleep(3000);
```

### 3. 复杂算法与边界条件 [R-ANN-10.03]

当逻辑有非直觉的处理时，注释解释为什么这样处理。

```java
// 先扣库存再创建订单，防止超卖
// 如果反过来，并发场景下可能出现库存扣减成功但订单创建失败的情况
if (!inventoryService.tryDeduct(sku, quantity)) {
    throw new InsufficientStockException(sku);
}
Order order = orderRepository.save(new Order(...));
```

### 4. 临时代码与 TODO [R-ANN-10.04]

> 判断标准：TODO 写清谁/何时/条件/后果；使用绝对日期；无“以后优化”式 TODO。

TODO 必须负责任：写清谁、什么时候、什么条件下需要处理，以及不处理的后果。

```java
// ✅ 负责任的 TODO
// TODO(zhangsan) [2026-09-01前] 短信服务商迁移至阿里云，当前使用的腾讯云通道将在9月底下线
// 详见 JIRA-3456
public void sendSms(String phone, String content) {
    tencentSmsService.send(phone, content);  // 临时保留旧通道
}

// ❌ 不负责任的 TODO
// TODO 以后优化
```

### 5. 异常处理注释 [R-ANN-10.05]

> 触发条件：catch 块吞掉异常或转换异常时。

> 判断标准：吞掉异常或异常转换时必须说明原因和失败去向；非吞掉/非转换的 catch 可不注释。

不是每个 catch 都要注释，但吞掉异常或异常转换时必须解释。

```java
try {
    paymentGateway.pay(order);
} catch (TimeoutException e) {
    // 支付超时不代表支付失败，后续通过查询接口确认结果，因此不抛异常
    log.warn("支付超时，将异步确认结果: orderId={}", order.getId(), e);
}
```

## 业务注释检查清单 [R-ANN-11]

> 触发条件：修改或审查业务代码注释时，按实际命中的代码类型选用下表对应项。
> 动作要求：表中“注释重点”即必须覆盖的信息维度，逐项覆盖命中项。
> 判断标准：命中项的注释同时给出表中“示例”对应的可核验内容；未命中项不适用。
> 失败或例外处理：无法判断代码类型是否命中时按“不适用”处理并在交付中说明判断依据；不得省略或编造示例内容。

| 代码类型 | 注释重点 | 示例 |
|----------|---------|------|
| 复杂 if 条件 | 业务含义 | `// 只有待支付且未过期的订单才能取消` |
| 魔法数字/阈值 | 来源与原因 | `// 超时时间=对方超时(5s) + 网络抖动(2s)` |
| 异常捕获 | 处理理由 | `// 非核心功能，失败不影响主流程` |

## 逻辑段落清单 [R-ANN-12]

> 触发条件：审查或规划方法体业务段落时。
> 动作要求：按用户操作/任务执行的业务时间线排列 1–15 项（前端 16–20 项）；适用项逐段覆盖。
> 判断标准：段落按时间线而非技术层排列；适用项在对应代码段前有注释；无连续业务段落断层。
> 失败或例外处理：段落不适用时在审查计划说明理由；不得用技术层平铺替代业务时间线。

以下每项在适用时都是独立逻辑段落，应按用户操作或任务执行的业务时间线排列，而不是按类、方法或技术层平铺：

1. 用户操作、Controller、定时任务、事件监听器或上游方法的触发入口
2. 入参、登录上下文、缓存与临时状态准备
3. 参与人、角色、组织、权限或数据范围判断
4. 查询/写入条件构造及条件的业务含义
5. 每次 Mapper、DAO、Service 持久层调用或外部系统交互
6. 查询结果转 Map/Set、关联装配、聚合、排序、去重和批量回填
7. 单位、金额、日期、编码、状态或展示内容转换
8. 关键 if/switch/提前返回/continue 分支及其业务影响
9. 状态、流程节点、金额、敏感字段和权限结果处理
10. `BeanUtils.copyProperties`、临时字段或跨步骤对象可能覆盖业务字段的操作
11. 通知正文、附件、导出内容、响应对象或页面状态装配
12. 持久化写入、工作流推进、消息/邮件发送等副作用
13. 排序、分页、总数计算和最终响应构造
14. 异常、空结果、零影响行、历史脏数据和降级处理
15. 最终结果去向、部分成功语义及后续调用

### Vue / JavaScript 前端补充段落 [R-ANN-12.01]

16. 多请求的串行等待或并行执行原因；依赖关系、部分失败和最终状态提交时机
17. 查询/重置/分页/排序/导出是否使用同一数据源、筛选条件与总数口径

20. 最终页面状态、选中项、loading、弹窗关闭和后续导航如何收束，避免中间态或旧状态残留

## 禁止行为（关键示例） [R-ANN-13]

> 触发条件：编写或审查业务注释时。
> 动作要求：对照错误示例检查是否存在仅翻译代码、注释与代码行为不一致等反模式。
> 判断标准：注释包含业务信息；注释描述与代码行为完全一致；发现不一致时修正注释或代码。
> 失败或例外处理：无法确认注释与行为一致时标记待确认并暂停；不得保留“注释比缺失更危险”的状态。

### 错误示例 1：仅描述代码动作 [R-ANN-13.01]

```java
// ❌ 查询用户 / 设置用户名 / 保存用户——仅翻译代码，无业务信息

//    数据来源：sys_user 表；结果用途：后续判断用户角色和数据权限
User user = userMapper.selectById(userId);
```

### 错误示例 2：注释与代码行为不一致 [R-ANN-13.02]

```java
// ❌ 注释写"检查用户是否有管理员权限"，实际代码检查的是用户是否被禁用
// ✅ 注释必须与代码行为完全一致，否则注释比缺失更危险
```

## 历史代码处理 [R-ANN-14]

> 触发条件：修改历史方法且需要补注释或评估是否拆分时。
> 动作要求：默认保持方法结构，仅补当前方法业务段落；只有结构导致语义无法定位或跨层事务问题才按 design-principles 评估拆分。
> 判断标准：未为补注释拆分超长方法；关键业务段落有注释；旧注释不一致已更新/删除；原位修复补齐当前方法段落。
> 失败或例外处理：拆分可能改变事务边界/扩大测试范围时暂停并确认；不得以“历史代码”为由省略注释。

### 核心原则 [R-ANN-14.01]

> 判断标准：不要求为补注释拆分超长方法；仍必须添加业务注释；原位修复补齐当前方法段落；旧注释不一致必须更新/删除。

- **不要求为补注释而拆分超长历史方法**：单独补注释可完成审查且不改变方法结构时禁止拆分；仅当方法结构导致业务语义无法定位或存在跨层事务边界问题时，按 `~/.zcode/rules/design-principles.md`「结构化根治门槛」评估。拆分可能带来业务风险、改变事务边界或扩大测试范围。
- **但仍必须添加业务注释**：在不改变方法结构的前提下，为历史方法的关键业务逻辑段落添加注释
- 原位修复时补齐当前方法业务段落
- 新增独立业务能力时再按分层规范落入 Service
- 旧注释与现有代码不一致时必须更新或删除

**不要求拆分** ≠ **不需要注释**：

| 场景 | 正确做法 |
|------|----------|
| 历史方法很长（如 200+ 行） | 保持方法结构不变，在关键业务逻辑段落添加注释 |
| 历史方法有复杂的业务逻辑 | 为每个逻辑段落添加注释，解释"为什么存在、数据从哪来、处理后到哪里去" |
| 历史方法直接调 Mapper | 不因为分层问题而重构，但在 Mapper 调用处添加业务注释 |
| 历史方法有 Controller 业务逻辑 | 不因为分层问题而迁移，但在业务逻辑处添加注释 |

## 注释反模式 [R-ANN-15]

> 触发条件：编写或审查注释时。
> 动作要求：逐项检查注释代码块、情绪化注释、过度注释、机械编号、枚举塞 <p>、自证性注释。
> 判断标准：6 类反模式均未出现；发现即删除或改写为业务注释；代码块与死代码按工程规则处理。
> 失败或例外处理：删除注释代码块前确认版本控制可恢复；有业务信息时先改写为业务注释再删除。

| 反模式 | 示例 | 问题 |
|--------|------|------|
| 注释代码块 | `// 旧实现: if (v1) ...` | 版本控制系统会保留历史，直接删掉 |
| 情绪化注释 | `// 前任写的烂代码，忍着吧` | 负能量且无信息量 |
| 过度注释 | 每行一个 `//` | 信噪比极低，埋没真正有用的信息 |
| 只有机械编号的阶段注释 | `// step1: 处理`、`// step2: 处理` | 没有业务名称和数据流信息；长历史方法可使用“第一步：获取合同基础信息”等业务阶段标题，但仍须补阶段内来源、目的和结果去向 |
| **枚举塞 `<p>`** | **5 项功能用顿号连在一行 `<p>` 里** | **超过 2 项必须用 `<ul>/<li>` 列表** |
| **自证性注释** | `// 最后url都没用到，直接使用的 authUrl` | 注释为死代码辩护而非说明业务语义；必须删除死赋值并删除该注释，其中业务信息改写为对应代码段的业务注释 |
