# 开发工作流

> 决策优先级见 `~/.zcode/AGENTS.md`「决策优先级」。
> 工程规范见 `~/.zcode/rules/engineering-core.md`；设计模式见 `~/.zcode/rules/design-principles.md`；注释标准见 `~/.zcode/rules/annotation.md`；陷阱见 `~/.zcode/rules/pitfalls.md`。
>
> **项目实例标注**：本文件中的 `wechatmodule`、`zygl`、`label_XXXtext`、Vue 2、Element UI 等为当前项目实例，仅适用于当前项目；其他项目按各步骤的核验目标（字段、数据源、查询契约、校验、显隐、提交契约、跨端接力）执行，模块名与接口路径以项目级 `AGENTS.md` 和实际代码为准。判断标准：核验步骤能对应到规则主体；引用项目实例时已标明其为当前项目事实。失败或例外处理：项目结构与实例不符时，按实际结构执行同等核验，不得因实例不适用而跳过步骤。

## 核心原则 [R-WFL-01]

> 触发条件：开始任何开发任务时。
> 动作要求：一次只解决已确认问题；历史最小修复；新增组件化；修改后全方法注释复查；每次编辑后影响面审查；无验证不声明完成；外部通知用隔离验证；分析与实施分离；设计前 HARD-GATE。
> 判断标准：任务范围可对应到用户指令；修改/验证证据可定位；未确认业务边界未实施；外部通知未发真实接收人。
> 失败或例外处理：业务语义/权限/金额/状态/审批/事务/跨模块接口未明确时暂停并走 HARD-GATE；不得边排查边修改。

- 一次只解决已确认的问题；判断标准：任务含多个独立问题时，按用户指令顺序或依赖关系逐个处理，每个问题完成验证后再进入下一个，不在同一轮修改中混入无关问题。
- 历史代码默认最小修复，不顺手做架构重构
- 新增代码按 `~/.zcode/rules/design-principles.md` 评估设计模式，前端新增组件按 `~/.zcode/rules/frontend.md` 组件抽取标准；设计模式按选用原则优先采用
- 修改方法后必须执行全方法业务注释复查
- **每次代码编辑后必须执行影响面审查**，确认修改不波及无关功能
- 无验证证据时不得声明完成；判断标准：声明"完成"必须以实际执行的验证命令、输入场景与结果（编译输出、测试输出、页面状态、接口响应等）为依据；无验证证据时须明确报告"未验证"及阻断原因。
- 短信、企业微信、邮件和推送等外部通知变更，默认使用样例断言、mock/stub 或隔离测试接收端验证内容、接收路由和缺失字段分支；未经本次任务明确授权，不得向真实接收人发送测试消息。
- **分析与实施分离（禁止边排查边修改）**：凡需先排查或定位才能确定修改方案的任务，必须按「先分析 → 输出报告 → 征得用户同意 → 再实施」顺序执行；在分析报告获用户同意前，不得对本会话任何文件执行修改（含 Edit/Write 及等价的文件写副作用）。判断标准：从收到任务到实施之间必经一次用户对方案与范围的明确同意，且只修改报告中被批准的部分。例外：用户已在本条指令中给出直接且无歧义的实施指令（已点名文件、方法、字段及期望结果）时，该指令即构成授权，不重复索取报告同意，但仍须执行适用的编辑前检查与影响面审查；分析过程中也不得顺手修改与本轮排查无直接因果关系的代码。
- **设计前 HARD-GATE**：只要实施仍依赖未明确的业务语义、权限差异、金额口径、状态流转、审批/工作流、事务边界、跨模块接口或存在多种会改变行为的技术方案，无论改动看起来多小，都必须先探索事实、指出缺失决策、比较可行方案并等待用户批准。用户仅点名文件、字段、方法或期望结果，不等于已经决定上述业务规则。只有用户已逐项明确行为与范围，且代码、数据和现有规则中不存在仍待取舍的业务假设时，才不重复索取方案批准；风险判定、路径核验、注释审查和验证门槛仍须执行。规则维护另按全局 `AGENTS.md` R 档执行。

## 操作风险与授权执行 [R-WFL-02]

> 触发条件：执行任何修改或状态变更前。
> 动作要求：按 AGENTS.md 判定 L1/L2/L3；L2 授权只覆盖点名操作/文件/字段/本次任务；L3 拒绝。
> 判断标准：风险等级有依据；授权范围可定位；未把 allowlist 当授权；未拆分命令规避 L3。
> 失败或例外处理：授权泛化/范围扩大/后续任务时重新授权；L3 提供安全替代。

- 按全局 `AGENTS.md` 判定 L1/L2/L3；风险判定与设计、业务假设及注释门槛相互独立。
- 用户直接且无歧义的实施指令，或对精确方案的批准，构成对应范围的 L2 授权；完成其余适用检查后立即执行，不再以笼统安全条款拒绝或重复索取同一授权。该授权不替代 `~/.zcode/rules/business-assumptions.md` 的业务假设确认、全局 `~/.zcode/AGENTS.md`「编辑前硬规则」或其他独立质量门槛。
- 授权仅覆盖用户点名的操作、文件、字段和本次任务；需求变化、范围扩大或后续任务必须重新授权。
- 工具权限 allowlist 只表示工具可调用，不代表用户已授权具体 L2 操作。
- L3 直接拒绝，不得通过拆分命令、改写工具或要求用户重复确认来规避。

## 流程路由 [R-WFL-03]

> 触发条件：接到 Bug 修复、新增功能、设计、代码审查、交付、前端性能、图表、多端对齐任务时。
> 动作要求：按表格选择对应规范与流程；Skill 调用遵循更高优先级和用户显式 /命令。
> 判断标准：任务能对应到表格场景；执行步骤与对应规范一致；未自动调用的 Skill 按显式请求/触发条件。
> 失败或例外处理：场景无对应路由时按 AGENTS.md 决策优先级和最近专项规则处理，并说明依据。

| 场景 | 详细规范 | 说明 |
|------|---------|------|
| Bug 修复 | 本文件核心原则 + `~/.zcode/rules/engineering-core.md` | 复现 -> 追踪 -> 诊断 -> 修复 -> 注释复查 -> 验证 -> 相邻回归 |
| 新增功能 | 本文件核心原则 + `~/.zcode/rules/business-assumptions.md` + `~/.zcode/rules/design-principles.md` | 需求理解 -> 业务规则确认 -> 影响分析 -> 接口设计 -> 实现 -> 注释 -> 测试 |
| 设计前流程 | 本文件 HARD-GATE | 探索 -> 澄清 -> 方案比较 -> 呈现设计 -> 用户批准 |
| 代码审查 | `~/.zcode/rules/delivery.md` 交付要求 + `~/.zcode/rules/engineering-core.md` 完成检查 | 按业务正确性、安全、权限、事务、性能、并发和交互逐项核对 |
| 交付 | `~/.zcode/rules/delivery.md` | 标准交付结构模板 |
| 前端性能（页面无响应/卡顿） | `~/.zcode/rules/engineering-core.md`「前端性能排查：浏览器「此页面无响应」」 | Trace + 网络请求 + 控制台错误 -> 定位瓶颈 -> 验证 |
| 图表与可视化 | `archify` 技能（用户明确要求时） | 先确认数据、受众和输出介质，再设计和验证 |
| 多端同步改造/迁移/对齐 | 本文件「多端业务一致性对齐」+ `~/.zcode/rules/business-assumptions.md`「多端数据来源一致性门控（强制）」 | 全维度核验 + 跨端数据接力闭环验证 |

各场景按本文件与对应 rules 执行；Skill 调用遵循更高优先级运行时指令，用户显式 `/命令` 直接调用。上级要求命中 Skill 时自动调用的，按要求执行；其余场景按本文件的触发条件执行。

## 规则文件维护（R 档执行流程） [R-WFL-04]

> 触发条件：维护 AGENTS.md、rules/*.md、技能规则或其他影响后续行为的上下文文件时。
> 动作要求：按 发现→追溯→比较→批准→实施→验证 执行；语义变化先取得精确差异和文件范围批准；去重保留权威来源。
> 判断标准：6 步均有记录；逐文件原始/优化条目数、等价合并、未修改条目、冲突消解、批准清单、增删明细可定位；规则数未减少。
> 失败或例外处理：发现削弱或规则数减少时停止并说明；不得以精简/澄清/去重为名削弱规则。

全局 `~/.zcode/AGENTS.md`「规则文件维护（R 档）」是 R 档的最高级门槛，本节只规定执行顺序，不另行放宽或重定义其强制项。"削弱"的完整定义（6 类）见 `~/.zcode/AGENTS.md`「规则文件维护（R 档）」。

1. **发现**：完整读取目标规则文件，并检索同一概念在顶层规则、专项细则、模板、示例和检查清单中的全部落点。
2. **追溯**：为每项拟修改内容标明来源；用户明确约定和最高级规则优先于历史摘要、旧会话推测或下级重复文本。
3. **比较**：展示精确旧文本、新文本、影响文件和强度分类；发现削弱时停止，不得将其包装成等价精简。
4. **批准**：语义变化取得用户对精确差异和文件范围的批准；纯格式、错别字和失效引用修复按全局规则直接处理。
5. **实施**：由主代理在批准范围内编辑；不得借同步之名扩大到未列明文件或引入新约束。
6. **验证**：扫描旧措辞残留、重复定义、错误引用、Markdown 结构及正文—模板—清单一致性；逐项说明增强能力是否仍可被实际验收。

规则去重必须保留一个明确的权威来源和所有必要的可执行引用。删除下级重复文本前，先确认权威来源已覆盖原有强度、默认值、例外和验收项；否则属于削弱，不得删除。

## 修改后影响面审查（强制） [R-WFL-05]

> 触发条件：Bug 修复、新增功能或涉及共享类/注解/Service 的 Edit/Write 完成后。
> 动作要求：检查共享依赖、调用链平行实现、注解传播、全链路数据流；Grep 引用方并确认同步/排除理由。
> 判断标准：审查结论写入交付「审查与影响面」；共享依赖/平行实现/注解/数据流均有结论；需改的已补充，不改的有排除理由。
> 失败或例外处理：无法确认引用方时标记未验证；不得仅口头完成审查。

**每次代码编辑完成后，必须执行一次影响面审查，确认本次修改不会波及无关功能。审查结论必须写入当次交付回复的「审查与影响面」段落，不得仅在会话过程中口头完成。**

### 触发时机 [R-WFL-05.01]

> 判断标准：Bug 修复、新增功能、共享类/注解/Service 修改后均触发；缺任一场景即未执行影响面审查。

- Bug 修复的 Edit/Write 完成后
- 新增功能的 Edit/Write 完成后
- 任何涉及共享类、共享注解、共享 Service 的修改后

### 审查内容 [R-WFL-05.02]

> 触发条件：执行影响面审查时。
> 判断标准：共享依赖、调用链、注解传播、数据流、既有入口可达性五项均有结论；需改的已补充，不改的有排除理由。

1. **共享依赖检查**：修改的类/注解/接口是否被其他模块引用（grep 类名、注解名、方法名）
2. **调用链覆盖**：同一方法是否在其他 Service 中有平行实现（如同名 compare 方法）
3. **注解传播**：修改注解值后，所有使用该注解的代码路径是否都能正确处理新值
4. **数据流完整性**：修改字段映射/转换逻辑后，前端赋值、后端装配、导出、邮件通知等全链路是否一致
5. **既有入口可达性**：数据准入范围、状态口径或字段来源变更后，逐个确认依赖该数据的既有操作入口（发送、导出、打印、审批等）仍能取到其所需字段；不得只验证列表展示

### 审查方法 [R-WFL-05.03]

> 触发条件：执行影响面审查时。
> 动作要求：Grep 修改的类名/注解名/方法名，逐个确认引用方是否需要同步修改。
> 判断标准：Grep 命中清单与逐个引用方的「同步修改/排除理由」均可定位。
> 失败或例外处理：无法确认引用方时标记未验证并说明阻断，不得默认排除。

Grep 修改的类名/注解名 -> 逐个确认引用方是否需要同步修改 -> 需要改的立即补充，不需要的记录排除理由。

### 与完整代码审查的关系 [R-WFL-05.04]

> 判断标准：轻量影响面审查与交付前完整审查均执行；前者聚焦波及面，后者按业务正确性/安全/权限/事务/性能/并发/前端交互逐维度核对。

轻量自查（每次 Edit 后）聚焦「是否波及无关功能」；交付前完整审查按业务正确性、安全、权限、事务、性能、并发和前端交互逐维度核对。

### 与 `~/.zcode/rules/engineering-core.md`「修改后全方法审查」的关系 [R-WFL-05.05]

> 触发条件：需要区分影响面审查与全方法审查时。
> 判断标准：影响面审查与全方法审查均执行；前者聚焦跨方法/跨模块，后者聚焦方法内业务段落；不得互相替代。

两者互补，均需执行，聚焦不同：
- **本审查（影响面）**：聚焦跨方法/跨模块，确认修改不波及无关功能。
- **全方法审查**：聚焦方法内，审查被修改方法的全部业务逻辑段落，见 `~/.zcode/rules/engineering-core.md`「修改后全方法审查」。

### 多模型交叉审查（可选执行，必须评估） [R-WFL-05.06]

> 判断标准：涉及事务/并发/权限/跨模块接口/公共组件或预期≥4 文件时，已评估是否需要独立交叉审查；不采用时交付写明排除理由；交叉审查结果仅作主代理复核材料。
> 失败或例外处理：无法进行独立复核时说明阻断；不得把未执行的交叉审查表述为已完成。

当修改同时涉及事务、并发、权限、跨模块接口、公共组件，或预期修改不少于 4 个文件时，必须评估是否需要独立交叉审查；若不采用，交付中写明排除理由。交叉审查结果只能作为主代理复核材料，不替代主代理判断。

## 多端业务一致性对齐（强制） [R-WFL-06]

> 触发条件：多端同步改造、迁移、功能对齐，或共享接口/字典/枚举/状态机/工作流变更时。
> 动作要求：按 Tier 1/Tier 2 执行对应步骤；逐字段核对入口/字段/顺序/标签/下拉/列表查询/校验/显隐/自动计算/禁用态/流程/提交契约；完成跨端接力闭环。
> 判断标准：目标端运行时字段集/顺序/标签/数据源/查询契约/校验/显隐/自动计算/禁用视觉与源端一致；任一端提交的单据可在其他端完整回显并续办。
> 失败或例外处理：静态代码或仅数据模型一致不足以宣称对齐；运行时不可用时记录缺失条件和未验证范围。

执行步骤清单以 multi-end-align skill 为载体。本节为多端规则权威；12 步执行清单以 skill 为载体，两份清单必须同步，Tier 1 均含步骤 12。

**触发条件**：以下任一场景触发本节：
1. 将 A 端（如 PC）的功能在 B 端（如移动端/微信端/小程序）复刻或对齐；
2. 同一业务在多个前端仓（如 PC Web / 移动 H5 / 微信端 / 微前端）存在平行实现，任一端进行同步改造、迁移或 Bug 修复；
3. 多端共享的后端接口、字典、枚举值、状态机或工作流变更，可能波及任一端的数据写入或续办。

**核心目标（跨端业务接力）**：任一端（如 APP）产生的数据，其他端（如 PC）必须能无差别回显并继续下一步操作（续办、审核、变更、打印等），业务规则、流程状态与数据口径强一致；页面外观相似不等于对齐完成。

**分级要求**：
- **Tier 1（小规模改动，变更 ≤5 个字段或仅修复已有对齐 Bug）**：必须执行步骤 1（源端字段清单）、5（下拉与列表/搜索查询契约）、11（提交契约）、12（运行时验证与跨端接力闭环），以及受影响字段的步骤 4（标签）、6（禁用状态）、7（校验规则）
- **Tier 2（首次对齐或大规模改动，变更 >5 个字段或新增完整功能端）**：必须执行全部 12 个步骤

**禁止行为**：
- 仅比对数据模型字段（DTO/Entity）就宣称一致；数据模型中有字段不代表目标端模板中有绑定
- 仅读取源端静态代码中的 v-model 绑定就断言字段列表；低代码生成页面的标签通过 `label_XXXtext` 变量控制，不在模板标签文本中
- 未对比字段顺序、标签文案、禁用状态、下拉数据源、校验规则和列表/搜索查询契约（筛选条件、默认条件、分页参数、排序与总数口径）就声称对齐
- 假设数据源一致；同名 API 文件可能来自不同模块，接口返回数据域不同（如 `wechatmodule` vs `zygl`）
- 仅对齐最终渲染的可见字段集，未对齐动态显隐的触发条件与联动链；触发条件不同时，业务场景一变就会出现字段缺失或多余。显隐联动属于业务逻辑一致性，不得以「合法端适配」为由省略联动链
- 未验证「A 端提交、B 端续办」的数据闭环就宣称多端一致；静态页面一致不保证接力可用
- 假设两端的枚举值、状态值、单位、精度口径一致；一端本地映射（如写死的类别对照）与另一端字典 API 混用时，值域漂移会导致对端显示编码或校验失败

**低代码生成页面的常见分歧源**：目标端页面若由低代码平台生成（如固定模板命名、`label_XXXtext` 变量控制标签），其操作逻辑（作废、删除、提交等）独立于源端实现——低代码页面调用通用 CRUD 接口，不继承源端手写页面的业务校验与副作用；对每处操作仍须逐个比对后端接口 URL、入参结构和状态值口径后确认，不得因“低代码独立实现”这一规律跳过比对。此类页面的高频分歧包括：使用通用 CRUD 接口而非业务专用接口（丢失前置校验和副作用字段）、硬编码非标准状态值（与字典不一致）、缺少源端已有的前置校验接口调用、弹窗输入值未传递给后端。对齐时必须逐个比对操作对应的后端接口 URL、入参结构和状态值口径，不得因目标端已有同名方法名就假设一致。

**必执行的对齐核验步骤**：

1. **源端运行时字段清单**：使用浏览器 DevTools 或 `mcp__chrome-devtools__evaluate_script` 提取源端页面所有可见表单控件的 label、value、disabled 状态；不得仅靠静态代码提取。使用 DevTools 需用户当前任务明确授权；未授权时改用 `preview_*`、静态解析或项目日志，并记录未验证范围。
2. **目标端数据模型覆盖度**：逐字段核对目标端数据模型是否包含源端所有字段；缺失字段必须补齐
3. **模板绑定覆盖度**：逐字段核对目标端模板是否绑定了源端所有可见字段；未绑定字段不得声称对齐
4. **字段顺序与标签**：对比源端与目标端每个 Tab/分区的字段顺序和中文标签；标签必须与源端完全一致（包括括号、"甲方/乙方"等修饰词）
5. **下拉与列表/搜索查询契约**：对比每个下拉字段的接口 URL、查询参数和响应格式，同名字段可能来自不同数据域；同时对比列表/搜索接口的查询契约——筛选条件（状态过滤、时间范围、关键字匹配字段、组织/权限范围）、默认查询条件、分页参数约定、排序字段与方向、总数口径。两端列表查询条件不同会得到不同结果集，即使下拉源一致也不得判定对齐；读侧查询契约核验见 `~/.zcode/rules/business-assumptions.md`「多端数据来源一致性门控（强制）」
6. **禁用/只读状态与禁用视觉样式**：对比每个字段在源端的 disabled/readonly 状态；如银行字段在源端为自动回填禁用，目标端不得开放编辑。同时逐字段比对禁用态的视觉呈现——背景色（置灰）、文字颜色（变灰）、`cursor: not-allowed`、opacity/透明度、可聚焦性；目标端「仅 disabled 属性但无置灰样式」判为不合格（用户会把禁用字段误判为可点击却点不动的 Bug）
7. **校验规则**：逐字段对比源端与目标端的必填性、格式、长度/范围限制和自定义校验消息；一端拦截的非法值不得在另一端放行提交
8. **动态显隐规则（业务逻辑一致性）**：逐字段提取源端的显隐控制（v-if/v-show 条件、字段联动链、低代码 `hidden` 绑定与 `label_XXXtext` 控制），提取完整联动链——触发字段、条件表达式、受影响字段、触发时机，在目标端复刻相同触发条件与联动链；仅复刻「当前场景下的可见集」不算对齐。显隐联动属于业务逻辑一致性，不属于 `~/.zcode/rules/frontend.md` 允许的布局/组件端适配差异，不得以屏幕尺寸、组件库或输入方式差异为由省略联动链。判断标准：相同输入组合下，A/B 两端每个字段的可见性、禁用态、禁用视觉样式逐字段一致
9. **业务逻辑与自动计算**：对比联动赋值、自动回填、自动计算（如价格区间、单位换算、金额汇总）的公式、触发时机、精度与舍入口径；计算结果参与提交时，两端提交值必须同口径
10. **流程步骤与操作入口**：对比单据状态机、每个状态下的可用操作（提交/撤回/审核/驳回/变更等）、按钮禁用条件、防重复提交与操作确认等交互防护；任一端可达的流程路径不得在另一端断链
11. **提交契约**：对比保存/提交接口的 URL、入参字段名、必填性、枚举与状态值域、单位与精度、附件关联方式；读侧数据源门控见 `~/.zcode/rules/business-assumptions.md`「多端数据来源一致性门控（强制）」。同时验证目标端 API 文件（如 `src/api/xxx.js`）中是否已包含所需的业务专用方法（如作废、校验接口），若缺失须在同次修改中补齐；方法 URL 必须与源端一致（注意目标端 `PREFIX` 值可能为空导致路径无前缀）
12. **运行时验证与跨端接力闭环**：对齐完成后，在目标端浏览器逐 Tab 截图与源端逐字段比对；并在 A 端使用测试环境数据真实提交一条单据（测试环境提交需用户当前任务明确授权，不得写入生产环境），然后于 B 端打开同一单据，验证字段回显完整、动态显隐、禁用状态与禁用视觉样式正确、可继续下一步操作且不被未知枚举/必填缺失/校验规则阻断；不得仅凭代码审查宣称完成

**多端一致性补强执行项（强制）**：

- **字段动态显隐核对**：适用端类型为 PC Web、移动 H5、微信端、小程序、微前端和低代码页面。动作要求：逐字段读取源端与目标端运行时 DOM、Vue 实例和低代码 `hidden` / `label_XXXtext` 绑定，记录 visible/display、disabled/readonly、触发字段、条件表达式、触发时机和受影响字段集合，并按初始化、字段变更、提交前三组输入状态执行。判断标准：每个字段输出 `BP-DYNVIS-<field>: PASS/FAIL | source expression | target expression | trigger | affected fields | evidence`，全部为 `PASS` 才算通过。失败处理：任一字段为 `FAIL` 时不得宣称对齐；修复后重测全部三组输入状态；运行时不可用时记录缺失条件、未验证范围和下一步动作。
- **多字段联动核对**：适用端类型为 PC Web、移动 H5、微信端、小程序、微前端和低代码页面。动作要求：从字段变更、初始化和提交前事件链提取联动依赖图，比对触发字段、源值、目标值、公式、触发时机、精度、单位换算和提交值；每个联动路径记录到源端与目标端。判断标准：每个依赖路径输出 `BP-LINK-<source-field>: PASS/FAIL | dependencies | expressions | trigger | commit value | evidence`，依赖图、提交值和精度口径全部一致才算通过。失败处理：任一路径、公式、精度或提交口径不一致即阻断；无法运行时验证时记录缺失条件、未验证范围和下一步动作。
- **字段顺序与布局对齐核对**：适用端类型为 PC Web、移动 H5、微信端、小程序、微前端和低代码页面；历史案例锚点为“APP 端代谢类委托单样品信息页签中的样品信息表单，前处理方式被孤立隔断，应保持与 PC 一致的字段顺序”。动作要求：读取源端与目标端每个 Tab/分区的运行时 DOM，比对字段顺序数组、中文标签、可见性、禁用态、父容器、布局上下文和同屏坐标；重点核对同一表单内前处理方式等字段不得被孤立隔断。判断标准：每个分区输出 `BP-LAYOUT-<tab>: PASS/FAIL | expected order | actual order | label diff | container | coordinate diff | evidence`；字段顺序数组完全一致、标签 diff 为 0、字段不被孤立隔断，才可判定通过。失败处理：顺序、标签、父容器、布局上下文或孤立隔断任一不合格即阻断；运行时不可用时记录未验证范围和静态 DOM 证据。
- **端间数据接力核对**：适用端类型为多端均有保存/提交或打开/续办入口的单据和流程。动作要求：从 A 端保存或提交入口创建或选择真实单据，在 B 端打开、续办、审核或变更入口比对字段回显、枚举与状态值域、必填性、单位与精度、附件可见/可下载/可编辑、后续操作可用性。判断标准：每个接力场景输出 `BP-RELAY-<case-id>: PASS/FAIL | submit end | receive end | fields | enums | attachments | next action | evidence`；字段完整、值域可识别、附件可用且后续操作不被阻断才可判定通过。失败处理：任一字段缺失、枚举未知、附件断链或后续操作被阻断即不得宣称对齐；环境阻断时记录缺失条件和未验证范围。

**验证标准**：目标端运行时页面的字段集、顺序、标签、数据源、列表/搜索查询契约（筛选条件、默认条件、分页参数、排序、总数口径）、校验规则、动态显隐、自动计算、禁用状态与禁用视觉样式（背景色、文字色、cursor、opacity/透明度、可聚焦性）与源端完全一致，无遗漏、无多余、无标签偏差、无结果集差异；且任一端提交的单据在其他端可完整回显并无差别继续下一步操作，无字段缺失、无校验阻断、无流程断链。

## 历史代码修改 [R-WFL-07]

> 动作要求：保持业务结果、控制最小范围、补齐注释、不因分层扩大重构；按 engineering-core 渐进式架构治理处理。
> 判断标准：修改范围对应根因/用户要求；业务结果不变；注释补齐；无无关重构。
> 失败或例外处理：需扩大重构或改变事务/权限/接口边界时按 HARD-GATE 确认。

允许原位修复的场景及处理要求见 `~/.zcode/rules/engineering-core.md`「渐进式架构治理」。核心：保持业务结果、控制最小范围、补齐注释、不因分层问题扩大重构。

触发条件：判断历史遗留整改与注释补齐范围时。动作要求：按下列口径界定触及范围，只整改触及方法。「触及」口径见 `~/.zcode/AGENTS.md`「决策优先级」[R-AGT-03]：触及 = 本次 diff 直接修改的文件及其中被直接修改的方法/函数/事件链；历史遗留整改与注释补齐以触及方法为限，未触及范围不主动整改，发现时列入交付「后续建议」。判断标准：修改范围与触及清单一致；未触及项已列入「后续建议」。失败或例外处理：无法判断是否触及时按未触及处理，不得扩大范围。

## 变更影响面审查（强制） [R-WFL-09]

> 触发条件：修改或新增任何需求、字段、数据来源或业务约束（含允许为空、必填、默认值、枚举值域、关联对象有无、准入范围），或收到与之相关的 Bug 修复、配置变更时；硬规则定义见全局 `~/.zcode/AGENTS.md`「变更影响面闭环审查」第 14 节。
> 动作要求：实施前按 10 个检索维度全局检索全部引用点，逐点给出「引用位置—影响结论—依据」；实施后闭环核对受影响点全部已修改或已记录待办。
> 判断标准：影响面清单覆盖全部检索命中点、各维度检索为 0 的维度声明、每个引用点的影响结论及依据；无悬空「受影响（待办）」；检索受阻时已按「未验证：[阻断原因]」披露；清单与逐点结论写入交付「审查与影响面」段落。
> 失败或例外处理：无法穷尽引用点（工具缺失、超大仓库、权限不足）时，列出已覆盖与未覆盖范围并按「未验证：[阻断原因]」披露，不得以局部检索结果宣称影响面清零；受影响点无法同批修改时，在交付「风险与未验证项」记录待办、阻塞条件与验证动作。

**背景与目标**：需求在局部维度修改后，若未全局检索其上下游引用点，会出现“约束已变更、消费方仍按旧约束取数”的跨环节失败。典型案例：项目维度变更为「积分项目不选合同」后，报告发送邮件环节仍从合同取销售邮箱，导致无合同项目的邮件发送失败。本节要求以闭环方式执行影响面审查，防止此类遗漏。

**实施前：按 10 个检索维度全局检索引用点**，逐点记录「引用位置（文件路径:行号）— 影响结论 — 依据」；每个维度即使检索为 0 也必须在清单中显式声明「已检索，命中 0」：

| # | 检索维度 | 检索示例 |
|---|---------|---------|
| 1 | 代码调用方 | grep 字段名、getter/setter、方法名、常量 |
| 2 | 接口契约 | Controller/DTO/VO 中该字段或参数的定义与消费方 |
| 3 | 邮件/短信/推送模板与发送逻辑 | 模板占位符、收件人/抄送人取数逻辑 |
| 4 | 导出/导入模板 | 模板表头、字段映射、数据验证 |
| 5 | 报表与统计口径 | SQL 统计、报表查询、汇总公式 |
| 6 | 前端页面与校验 | 表单绑定、显隐/禁用条件、必填与格式校验 |
| 7 | 定时任务 | @Scheduled/cron 任务中的取数与条件 |
| 8 | 配置与字典 | properties/yml、字典表、枚举映射 |
| 9 | 数据库约束与历史数据 | NOT NULL/默认值/外键、存量数据是否满足新约束 |
| 10 | 测试用例 | 断言、mock 数据、夹具中的字段取值 |

**逐点结论限定三类**：`受影响（已同步修改）` / `受影响（待办，写明阻塞条件与验证动作）` / `不受影响（写明排除依据）`；三类之外的表述（如“应该没影响”“暂时不动”）判为不合格。

**实施后闭环核对**：逐点核对影响面清单——受影响点已同步修改，或以「受影响（待办）」记录于交付「风险与未验证项」并写明阻塞条件与验证动作；确认无清单外新增引用点后，本次变更才可声明完成。

**与其他审查的关系**：
- 与「修改后影响面审查」（R-WFL-05）互补：R-WFL-05 聚焦共享依赖、平行实现、注解传播等**代码级波及面**；本节聚焦需求/字段/数据来源/约束变更的**业务级上下游引用点**。两者触发场景重叠时合并输出一份影响面清单，不省略任一维度。
- 与 `~/.zcode/rules/version-control.md`「DB 字段变更同步」：该细则针对字段增删改的持久层链路，是本节维度 1、2、9 的细化；命中字段变更时两者均执行。
- 与全局 `AGENTS.md`「批判性审查」第 8 项「多入口逐项核实」：影响面清单中的每个引用点按该条目要求逐项列路径、行号、触发条件与结论，不得用“部分入口”概括。

**清单输出格式**（写入交付「审查与影响面」段落）：

```text
| 引用点 | 位置（文件:行号） | 维度 | 结论 | 依据 |
|--------|------------------|------|------|------|
| 报告发送邮件取销售邮箱 | ReportMailService.java:88 | 3 | 受影响（待办：无合同项目改取 operator 邮箱，阻塞于方案确认） | 合同为空时 NPE |
| 项目定时同步 | SyncJob.java:120 | 7 | 不受影响 | 同步逻辑不读取合同字段 |
| （维度检索为 0 时）导出模板 | — | 4 | 已检索，命中 0 | grep 表头映射无命中 |
```
