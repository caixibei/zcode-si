# 业务假设与数据验证规则

> 决策优先级见 `~/.zcode/AGENTS.md`「决策优先级」。本文件聚焦「修改前必须验证，禁止假设直接修改」这一维度。
> 注释标准见 `~/.zcode/rules/annotation.md`，文件路径验证见 `~/.zcode/rules/engineering-core.md`。
>
> 触发条件：修改业务代码前，涉及业务规则、数据格式、权限差异的假设时。
> 动作要求：按各节门控先验证当前事实，再区分“可直接采用的事实”与“须用户决定的目标政策”，最后修改。
> 判断标准：本文件所有门控以“先验证当前事实、再确认目标政策、后修改”为通过条件；未确认假设不得进入实施。
> 失败或例外处理：数据库/接口/运行环境不可用，或目标政策无用户与项目来源时暂停，按四项阻断格式记录并询问用户。

## 核心原则 [R-BUS-01]

> 触发条件：修改代码前，凡涉及业务规则、数据格式、权限差异的假设时。
> 动作要求：先验证当前事实，再区分“可直接采用的事实”和“必须由用户决定的目标政策”；用户已明确规则时不重复询问。
> 判断标准：每个关键业务边界能指出确认来源（用户本次指令/项目约定/已核实业务规则）；无未经确认且会改变实施结果的假设。
> 失败或例外处理：数据库/接口/运行环境不可用时按四项阻断格式记录，不得把静态推断表述为已验证。

**修改代码前，凡涉及业务规则、数据格式、权限差异的假设，必须先验证再动手。**
代码、数据库、接口响应和历史行为只能证明“当前实现或当前数据是什么”，不能替用户决定“目标业务政策应该是什么”。用户已在本次指令中逐项明确目标规则与范围时，不重复询问；仍须核实现状和影响面，防止按错误路径实施。
假设错误导致的返工是本项目最高频的摩擦来源。

## 一、业务规则假设门控（强制） [R-BUS-02]

### 触发条件 [R-BUS-02.01]

修改涉及以下任一场景，且目标规则尚未由用户本次指令、项目明确约定或已核实的业务规则确定时，**必须先向用户确认缺失的关键决策**，禁止自行假设并应用修复。用户仅点名文件、字段、方法或期望结果，只能确定修改触点或结果方向，不等于已经决定角色差异、计算口径、状态流转、审批路径、数据归属、并发模式或缺失字段策略。

| 场景 | 必须确认的内容 | 典型陷阱 |
|------|---------------|---------|
| 角色/权限差异 | 不同角色（管理员/普通用户/仓库管理员）的操作规则差异 | 管理员直出库不需要额度校验，但 agent 误标记为 Bug |
| 金额/额度计算 | 计算口径（累计/周期/阈值）、精度规则、舍入方式 | 额度是按年累计而非按月重置 |
| 状态流转 | 状态机定义、合法流转路径、历史数据兼容 | 某些状态下允许撤回但不重新生成变更记录 |
| 审批流程 | 审批节点、审批人角色、加签/转签规则 | 不同流程类型走不同的审批链 |
| 数据归属 | 数据属于哪个模块、哪个表、哪个业务域 | 同名 Entity 跨 5 个模块存在 |
| 并发模式 | 操作是单人负责还是多人抢审/抢操作 | 单人场景 `@Debounce` 够；多人抢审必须后端锁（悲观锁/CAS），`@Debounce` 防不了跨会话并发 |
| 对外通知字段缺失 | 字段缺失时取消整条通知、删除完整字段片段，还是按必填与可选字段分别处理 | 将“信息不发”误解为只隐藏空字段，或将可选字段缺失误判为整条通知不可发送 |

判断标准：命中任一场景且目标规则未由用户本次指令、项目明确约定或已核实业务规则确定时，必须先确认；用户仅点名文件、字段、方法或期望结果不构成业务规则确认。

### 事实证据与业务决策边界 [R-BUS-02.02]

> 判断标准：每条“事实”可指向代码/数据库/接口响应/配置；“目标政策”有用户或项目明确来源；不存在用当前实现替代目标政策的推断。
> 失败或例外处理：目标政策无来源时询问用户；不得把“现在这样运行”写成“应该这样运行”。

- **可从证据确认**：当前代码分支、数据库实际值、接口响应格式、现有角色配置和历史调用行为。
- **必须由用户决定**：目标权限政策、金额口径、合法状态路径、审批规则、数据归属、并发责任模型和对外通知缺失字段策略；项目已有明确约定时可直接采用该约定。
- **不得偷换**：当前系统“现在这样运行”不等于业务“应该继续这样运行”；代码中的历史实现也不能自动覆盖用户本次明确规则。
- **避免重复确认**：用户已明确目标行为、适用范围和关键边界时，直接按已确认规则实施，不得因本节再次索取同一决定。

### 执行流程 [R-BUS-02.03]

> 触发条件：识别到本次修改依赖的业务假设且目标规则未由用户、项目或已核实规则确定时。

```text
1. 识别假设 → 列出本次修改依赖的所有业务假设
2. 核实现状 → 用代码、数据库、接口响应或配置确认当前事实
3. 区分决策 → 标记哪些事实可直接采用，哪些目标政策仍须用户决定
4. 询问确认 → 每轮只询问一个会改变实施结果的关键问题；用户回答后重新评估剩余假设，仍有未决项时再进入下一轮
5. 记录规则 → 确认后将非直觉业务规则写入对应代码注释，防止后续误判
```

**判断标准**：交付中对每个已实施的关键业务边界（角色/权限、金额口径、状态流转、审批、数据归属、并发模式、通知缺失字段策略）均能指出确认来源（用户本次指令、项目明确约定或已核实业务规则）；不存在未经确认且会改变实施结果的假设被直接实施。

### 数据库或运行环境不可用时的阻断格式 [R-BUS-02.04]

> 触发条件：必须依赖数据库、接口或运行环境验证但无法连接/权限不足/服务未启动时。
> 动作要求：按“已确认事实、缺失条件、未验证范围、下一步动作”四项记录。
> 判断标准：四项完整；未验证范围具体到字段/分支/入口/结论；下一步是唯一最小动作。
> 失败或例外处理：四项未完整前不得将静态推断表述为已验证。

当必须依赖数据库、接口或运行环境验证但当前无法连接、权限不足或服务未启动时，交付中必须按以下四项记录：

1. **已确认事实**：来自当前代码、配置或已有日志的事实；
2. **缺失条件**：缺失的连接、权限、数据、服务或登录上下文；
3. **未验证范围**：受阻断影响的具体字段、分支、入口或业务结论；
4. **下一步动作**：唯一需要用户确认或执行的最小验证动作。

在上述四项未完整记录前，不得将静态推断表述为数据库或运行时已验证。

### 禁止行为 [R-BUS-02.05]

> 触发条件：准备按假设修改角色权限、额度周期、状态流转、数据归属、并发模式或通知缺失字段策略时。
> 判断标准：不存在自行假设角色权限相同、额度重置周期、状态流转路径后直接修改；不存在把当前代码/数据状态推断为目标政策；修复后未因假设错误返工。
> 失败或例外处理：发现假设错误时停止并按业务假设门控重新确认。

禁止自行假设角色权限相同、额度重置周期、状态流转路径后直接修改；禁止把当前代码或数据状态直接推断为目标业务政策。修复完成后才发现假设错误导致返工是典型反模式。

## 二、数据格式验证门控（强制） [R-BUS-03]

> 触发条件：字段显示编码/标签不一致、导出与查询结果不一致、两端数据类型/格式/参数不兼容时。
> 动作要求：先查数据库实际值/API 响应/字典映射，再追导出方法或数据产生端；禁止直接做类型转换或改数据层。
> 判断标准：差异根因可定位；修复产生问题的一端；同一输入在列表与导出/两端返回一致结果或已解释业务差异。
> 失败或例外处理：无法确认 API 返回格式或业务口径时暂停并询问；不得把当前存储值当作接口响应证据。

### 字典编码 vs 标签 [R-BUS-03.01]

> 触发条件：字段显示原始编码而非可读名称时。
> 动作要求：先数据库查实际值、再确认 API 返回格式、查字典映射；可编辑表格只在展示层修复。
> 判断标准：数据库值、API 响应、字典映射三者可定位；可编辑表格未改数据层；展示层修复后标签正确且编辑功能不受影响。
> 失败或例外处理：API 返回格式无法确认时暂停；不得仅凭数据库存储值推断接口返回。

字段显示原始编码而非可读名称时，**修改前必须验证**：

1. **数据库查询**：`SELECT * FROM table WHERE id = ?` 确认实际存储值
2. **API 响应检查**：确认接口返回格式。使用 Chrome DevTools MCP 时遵循 `frontend.md`「前端工程纪律」授权边界（用户在当前任务明确授权或要求后方可调用）；未授权时改用接口文档、前后端代码追踪、`preview_*` 工具或项目日志取证，并在交付中说明实际证据来源
3. **可编辑表格**：禁止改数据层——仅在展示层修复（template formatter/slot）
4. **字典表确认**：`SELECT * FROM sys_dict_item WHERE dict_type = 'xxx'` 确认映射存在

### 导出与查询方法差异 [R-BUS-03.02]

**触发条件**：导出结果与页面查询结果的数量、筛选范围、字段值或展示格式不一致时。

**必须执行**：先从导出按钮追踪实际请求 URL，再定位导出 Controller、Service 和 Mapper；禁止假设页面查询方法就是导出方法。详细排查流程见 `~/.zcode/rules/engineering-core.md`「导出数据不一致排查」。

**判断标准**：已逐项对比导出与页面查询的接口 URL、Controller/Service/Mapper 方法、筛选条件、字段映射、权限范围和空结果处理，并能指出差异引入点；修复后同一输入在两个路径返回一致结果或已解释业务差异。

### 数据类型与格式不一致（强制） [R-BUS-03.03]

发现两端数据类型、格式或参数不兼容时，**禁止直接做类型转换修复**，必须先执行 `engineering-core.md`「根因分析原则」的完整诊断流程。

**触发条件**：任一字段在不同端（PC/移动端/微信端/后端）的数据类型、格式、值域或参数结构存在不一致。

**执行流程**：

```text
1. 定位数据产生端（源端）：该字段最初由哪个端、哪个方法、哪个 API 产生
2. 核对接口契约：源端和消费端的 API 文档/DTO 定义中该字段的类型和格式
3. 追溯引入点：不一致是在哪一层引入的（前端赋值 → 序列化 → 网络传输 → 反序列化 → 后端处理）
4. 判断责任方：是源端实现偏离契约，还是消费端期望超出契约
5. 选择修复层级：修复产生问题的一端，不在消费端做兼容
```

**判断标准**：修复后，两端对该字段的类型、格式和值域完全一致，且修复不引入新的不兼容。

**典型反模式**：

- ❌ 移动端 `region` 发送 Object，直接在提交前 `normalizeRegion()` 转 String，而不追查 `region` 为何在移动端是 Object
- ❌ 枚举值不一致时在前端做硬编码映射，而不确认字典表和两端 API 的值域
- ❌ 接口参数缺失时在消费端加默认值，而不确认参数为何在源端未设置

## 三、文件路径验证门控（强制） [R-BUS-04]

> 触发条件：任何 Edit/Write 前。
> 动作要求：Grep 关键字 → Glob 同名候选 → 编辑前输出“将编辑 [完整路径]，因为 [关联]” → 再编辑。
> 判断标准：实际编辑路径与声明逐字一致；同名候选已全部列出并记录选择依据；Grep/Glob 命中可复核。
> 失败或例外处理：候选无法消歧或未找到目标文件时停止编辑，提出一个路径确认问题；不得假设文件路径。

> 本节为文件路径验证的完整规则（含同名文件高风险区域表、强制输出要求、禁止行为）；`engineering-core.md`「文件路径验证」指向本节。

编辑前**必须执行以下步骤，缺一不可**：

```text
1. Grep 目标函数名或关键字 → 获取候选文件列表
2. 若存在多个同名文件 → Glob 确认所有候选路径
3. 【强制输出】编辑前明确输出：
   「将编辑 [完整路径]，因为 [与当前 Bug 的关联]」
4. 确认路径后方可调用 Edit/Write
```

### 同名文件高风险区域 [R-BUS-04.01]

> 触发条件：Grep 命中多个同名文件或类名时。
> 判断标准：同名候选文件已全部列出；每个候选的模块/包路径与当前任务关联依据已记录；未仅凭类名选择第一个结果。
> 失败或例外处理：无法消歧时停止并询问；不得假设路径。

| 文件/类名 | 候选路径 | 风险 |
|-----------|---------|------|
| BpCommissionSheet | 5 个不同模块的同名类 | 改错模块的 Entity |
| crkls.vue | 多个模块目录下的同名文件 | 编辑了其他模块的页面 |
| ckgl 相关文件 | 出库管理、仓储管理多处 | 改错模块的页面 |

### 禁止行为 [R-BUS-04.02]

> 触发条件：编辑文件前，或 Grep 命中多个同名文件/类名时。
> 动作要求：先完成 R-BUS-04 的 Grep/Glob 定位与强制路径输出，再调用 Edit/Write。
> 失败或例外处理：候选无法消歧或未找到目标文件时停止编辑，提出一个路径确认问题。

- ❌ 假设文件路径直接编辑（83 次 File Not Found 错误的根因）
- ❌ 仅凭类名定位文件，不确认包路径
- ❌ 跳过同名文件检查直接选择第一个结果

**判断标准**：实际编辑目标路径与第 3 步强制输出声明的路径逐字一致；存在同名候选时已 Glob 确认全部候选路径并记录选择依据；Grep/Glob 命中清单可在会话中复核。

## 四、多端数据来源一致性门控（强制） [R-BUS-05]

### 核心原则 [R-BUS-05.01]

> 判断标准：下拉/搜索接口的 URL、参数、响应与源端一致；同名 API 不因名称相同被假设为同一数据域；目标端未直接引用不同业务域的旧接口。
> 失败或例外处理：无法运行时验证时记录缺失条件和未验证范围；不得以静态同名 API 判定一致。

**触发条件**：将 A 端（如 PC）的功能在 B 端（如移动端/小程序）对齐时，涉及下拉框、搜索弹窗、列表查询等需要调用后端接口的场景。

**核心原则**：同名 API 文件可能来自不同业务域，接口返回的数据集不同。不能因为目标端已有同名函数就假设数据一致。

### 执行流程 [R-BUS-05.02]

> 触发条件：将 A 端功能对齐到 B 端，涉及下拉、搜索弹窗或列表查询时。
> 判断标准：4 步全部完成；URL、参数、响应与源端一致；下拉选项与搜索结果无多余/缺失；无 400/422 参数格式错误。

1. **识别所有下拉/搜索接口**：逐字段列出源端每个下拉框实际调用的后端 URL（如 `/zygl/wtfgl/bpFirstParty/hussarQuery`）
2. **核对目标端 API 文件**：确认目标端引用的 API 文件路径与源端一致；若路径不同（如 `wechatmodule/entrustManagement` vs `zygl/wtfgl`），必须切换到源端同路径
3. **验证接口参数兼容性**：确认目标端传递的查询参数与源端接口的 DTO 定义匹配；不兼容时需适配（如分页接口 vs 非分页接口需在前端做分页转换）
4. **运行时验证**：在目标端浏览器中检查网络请求，确认请求 URL、参数和响应数据与源端一致

### 判断标准 [R-BUS-05.03]

> 触发条件：完成多端下拉、搜索或列表对齐后。

- 下拉框选项内容与源端完全一致（无多余项、无缺失项）
- 搜索结果与源端一致（使用相同数据域）
- 网络请求中无 400/422 参数格式错误

通过标准：上述三项全部满足；任一不满足即按执行流程修正并重新验证。

### 典型反模式 [R-BUS-05.04]

> 触发条件：多端下拉/搜索/列表对齐后检查反模式时。

- ❌ 目标端使用 `wechatmodule/entrustManagement/bpFirstParty/hussarQuery`，源端使用 `zygl/wtfgl/bpFirstParty/hussarQuery`，导致选项不同
- ❌ 源端使用非分页接口 `hussarQuery`，目标端 `filterPopup` 组件传入分页参数，导致空结果
- ❌ 目标端使用 `hussarQuerybpPartyAContactsSimpleCondition_6`，但该方法在目标端 API 文件中不存在

判断标准：上述反模式未出现；出现任一即按执行流程修正并重新验证。

### 读侧：列表/搜索查询契约一致性（强制） [R-BUS-05.05]

**触发条件**：将 A 端列表/搜索页面对齐到 B 端时，或任一端修改列表/搜索接口的查询条件、分页、排序或总数口径时。

**必须核对**：

1. 筛选条件：状态过滤、时间范围、关键字匹配字段、组织/权限范围在两端一致；A 端按状态过滤的列表，B 端不得省略或放宽该过滤。
2. 默认查询条件：首次进入页面的默认筛选值、默认排序在两端一致。
3. 分页参数约定：页码、每页条数、默认每页条数在两端一致；一端分页接口与另一端非分页接口混用时，须在数据产生端或统一契约处归一化。
4. 排序与总数口径：默认排序字段与方向、总数含义（返回记录数 vs 过滤前总数）两端一致。

**判断标准**：在相同查询条件下，A 端与 B 端列表返回的结果集（记录 ID 集合、顺序、总数）完全一致，无缺失、无多余、无顺序偏差。

**区分单端内部一致**：本节约束「跨端查询契约一致」；`engineering-core.md`「性能优化不得改变权限范围、过滤规则、排序口径和总数含义」、`frontend.md`「查询/重置/分页/排序调用同一数据接口」、`pitfalls.md`「查询、分页走不同接口」约束「单端内部一致」，两者不能互相替代。

**典型反模式**：

- ❌ B 端列表默认查询全部状态、A 端默认待审核，两端首屏结果集不同
- ❌ A 端按创建时间倒序、B 端按更新时间倒序，两端顺序不同
- ❌ A 端每页 50 条、B 端每页 10 条，逐页比对结果不一致

### 写侧：提交契约与跨端接力门控（强制） [R-BUS-05.06]

**触发条件**：同一单据/流程在多端均有写入或续办入口（如 APP 提交、PC 审核续办），或任一端新增字段、修改枚举值域/单位/精度/状态口径时。

**必须核对**：

1. 各端保存/提交接口的 URL 与入参字段名、必填性是否同源；不同端走不同 Controller 时，必须对比两者的持久化字段集
2. 枚举与字典值口径：任一端使用本地映射（如写死的类别对照）时，必须与字典表及对端口径核对值域；新增选项必须两端同步
3. 状态值与流程口径：状态字段值域、初始值、流转目标在各端一致；A 端写入的状态值必须落在 B 端可识别、可续办的值域内
4. 单位、精度与舍入：金额、数量、换算比等参与计算与提交的口径两端一致
5. 附件与关联数据：A 端上传的附件、子表明细在 B 端可见、可下载、可继续编辑

**判断标准**：A 端提交的单据在 B 端打开后，字段回显完整、显隐与禁用状态正确、能通过 B 端校验并完成下一步操作；不出现未知枚举、单位错位、必填缺失或状态断链。

**验证约束**：本门控的所有判断标准（附件可见、回显完整、状态断链等）均需运行时跨端验证，静态代码审查无法替代；环境阻断时须记录缺失条件和未验证范围。

**典型反模式**：

- ❌ 一端用本地映射维护「合同类别」，另一端走字典 API，值域不一致导致 PC 端显示原始编码或校验失败
- ❌ APP 端新增字段并提交，PC 端编辑页未同步该字段，用户续办保存时该字段被置空丢失
- ❌ 低代码生成页面使用通用 `insertOrUpdate` 接口执行作废/删除等操作，而非业务专用接口，导致前置校验丢失、副作用字段（如作废原因）未传递、状态值与源端不一致

### 禁用/只读态视觉样式一致性（强制） [R-BUS-05.07]

**触发条件**：多端对齐/同步或跨端接力时，源端任一字段处于禁用/只读态（含 disabled、readonly、自动回填只读、按钮禁用）。

**必须核对**：
1. 目标端该字段的 disabled/readonly 属性与源端一致，不得开放编辑；
2. 目标端禁用态视觉呈现与源端一致，逐字段比对：背景色（是否置灰）、文字颜色（是否变灰）、`cursor`（是否 `not-allowed`）、opacity/透明度、可聚焦性（是否可 focus/tab 进入）。

**判断标准**：属性一致且视觉呈现一致；目标端「仅 disabled 属性但无置灰样式」判为不合格——用户会把禁用字段误判为可点击却点不动的 Bug。验证方式：运行时段逐字段比对两端 computed style（背景色、文字色、cursor、opacity）或截图。

**典型反模式**：

- ❌ PC 端字段 disabled 且背景置灰、文字变灰，APP 端仅设置 disabled 属性但保持可编辑外观，用户误判为可点击
- ❌ 仅比对 disabled/readonly 属性就宣称一致，未比对禁用态的视觉呈现

### 联动显隐强一致性（强制） [R-BUS-05.08]

**触发条件**：源端存在任一字段的可见性或禁用态由另一字段值动态控制（v-if/v-show 条件、字段联动链、低代码 `hidden` 绑定与 `label_XXXtext` 控制）。

**必须核对**：提取源端完整联动链——触发字段、条件表达式、受影响字段、触发时机（初始化/变更/提交时）；在目标端复刻相同触发条件与联动链，不得只复刻某一场景下的最终可见集。

**判断标准**：相同输入组合下，A/B 两端每个字段的可见性、禁用态、禁用视觉样式逐字段一致；「仅复刻最终可见集」或「以合法端适配为由省略联动链」判为不合格。

**边界声明**：显隐联动属于业务逻辑一致性，不属于 `frontend.md` 允许的布局/组件端适配差异（屏幕尺寸、组件库、输入方式）；不得以端适配为由省略联动链。完整核验步骤见 `workflows.md`「多端业务一致性对齐」步骤 8。
