# 工程核心规范

> 决策优先级见 `~/.zcode/AGENTS.md`「决策优先级」，不在本文件重复。
> 设计模式与组件化决策见 design-principles.md。
> 历史代码修改流程见 `~/.zcode/rules/workflows.md`。

## 根因分析原则（强制）

修改任何代码前，必须先诊断问题的根因。数据不一致、格式不匹配或接口参数不兼容是**症状**，不是问题本身。

### 必须执行根因诊断的场景

| 场景 | 典型症状示例 |
|------|------------|
| 数据类型/格式不一致 | 一端发送 Object，另一端期望 String；日期格式 YYYY-MM-DD vs YYYY-MM-DD HH:mm:ss |
| 两端同名字段含义不同 | 同名 API 在不同模块返回不同数据域（如 `wechatmodule` vs `zygl`）|
| 枚举/字典值域不一致 | 一端用本地映射（硬编码），另一端用字典 API；或两端字典编码不同 |
| 接口参数缺失或多余 | 一端传分页参数，另一端接口不支持分页 |
| 相同功能在不同端表现不同 | PC 端正常，移动端异常；或新增/编辑正常，变更异常 |

### 根因诊断流程（强制步骤）

```text
1. 症状描述：用具体数据描述不一致（如"region 字段移动端发送 Object，后端期望 String"）
2. 根因排查：
   a. 检查该字段在源端（数据产生方）的原始定义和赋值逻辑
   b. 核对两端 API 接口契约（入参类型、返回格式）
   c. 追溯不一致的引入点：是源端实现偏离接口契约、目标端期望超出接口契约，还是中间层（序列化/反序列化）引入
   d. 确认该字段的业务语义和设计意图
3. 方案选择：
   a. 源端实现偏离接口契约 → 修复源端，不是在消费端做类型兼容
   b. 后端接口契约或设计偏离已确认的业务规范 → 向用户说明并确认是否调整
   c. 有意的兼容需求 → 用户明确确认后，在数据产生端（不是消费端）做归一化，并注释业务原因
4. 验证标准：修改后，问题不会再重复出现，且不引入新的业务风险
```

### 根因诊断验证清单

修改数据类型、格式或接口参数前，以下问题必须全部回答 yes：

```text
□ 我能说出不一致的根因是什么（不是症状）
□ 我的修复方案会消除根因而非掩盖症状
□ 修复后同一问题在其他字段、其他端、其他场景不会再出现
□ 我理解这个字段的业务语义和使用场景
□ 这个修改有用户指令、业务规则或接口契约的明确依据
```

### 禁止行为

- ❌ 未诊断根因就做类型转换/格式化/空值兜底（如 `String(obj.id || obj)` 可能掩盖数据来源错误）
- ❌ 用注释"兼容历史格式"掩盖不一致，而不追溯历史格式的产生原因
- ❌ 因为"PC 端也这样处理"就接受不一致，而不确认 PC 端的处理是否正确
- ❌ 把表面修复（如前端强制类型转换）包装成根因修复交付

## 安全编码

- SQL注入：禁止拼接用户输入，使用 MyBatis `#{}` 或参数化查询
- 输入校验：在系统边界校验长度、类型、范围和白名单
- 权限校验：删除、状态、金额和权限变更前验证当前用户权限
- 敏感信息：密码、密钥、token、连接串默认不得硬编码；经用户明确授权写入指定配置文件时，按 `version-control.md`「敏感配置」执行。日志、异常消息和用户可见输出始终不得记录完整敏感值。
- 文件上传：校验MIME、扩展名和大小，存入非Web直访路径
- 输出安全：用户可控内容进入HTML前防XSS
- 判断标准：代码审查中不存在字符串拼接 SQL；系统边界入参有长度、类型、范围或白名单校验；删除、状态、金额和权限变更前有权限校验；日志、异常消息和用户可见输出中无完整敏感值。

## 日志输出规范（强制）

- 触发条件：编写、修改或交付任何包含日志输出的代码（Java、JavaScript/TypeScript、Vue 等）；本次修改触及的文件或方法中存在历史遗留的标准输出/控制台打印语句时同样触发。
- 动作要求：
  1. 最终交付的代码不得以下列语句作为日志输出记录：Java 的 `System.out.print`/`System.out.println`、`System.err.print`/`System.err.println`、`e.printStackTrace()`；前端的 `console.log`、`console.info`、`console.debug`；`console.warn`/`console.error` 亦不得作为最终交付的日志手段。
  2. 需要保留的日志必须改用项目已接入的日志框架或封装输出：Java 按项目实际依赖（Log4j 2、Logback、SLF4J 门面等）使用对应 `logger.info`/`logger.warn`/`logger.error`，异常对象作为日志方法的最后一个参数传入，不用 `printStackTrace` 代替；前端改用项目现有日志或错误上报封装。
  3. 项目日志框架确认方式：Java 读取目标模块 `pom.xml`/`build.gradle` 的日志依赖与现有类的 logger 用法；前端检索项目内已有日志封装。确无任何日志机制且输出承载错误兜底信息时，在交付中列出位置并请用户确认保留方式，不得擅自引入新日志依赖。
  4. 历史遗留整改范围：本次新增代码与本次修改触及的方法/文件内的遗留标准输出语句，必须一并按上述框架整改，不得以「历史遗留」为由保留；本次未触及文件中的遗留语句不在本次修改范围，发现时列入交付「后续建议」。
- 判断标准：对本次修改的全部文件执行检索 `System\.(out|err)\.print|printStackTrace|console\.(log|info|debug)`，命中数为 0；或命中的每一处均有用户确认的保留依据并在交付中逐处列明。新增日志级别与语义匹配（错误路径用 error、可恢复异常用 warn、常规业务进度用 info/debug），不以 info 级别记录异常堆栈。

## 不合理代码残留整改（强制）

- 触发条件：编写、修改或交付任何代码。本次新增代码不得产生下列任一残留；本次修改触及的文件或方法中已存在下列残留时，同样触发整改。
- **不合理代码残留枚举**（命中任一即判定为残留，不存在「是否规范」的自由裁量）：
  1. **死赋值**：变量赋值后至作用域结束前没有任何读取点，如 `String url = authUrl;` 之后 `url` 再未出现。判定方法：检索该变量在赋值语句之后的全部引用，引用数为 0 即死赋值。
  2. **先赋值后覆盖**：同一变量在被读取前被二次赋值，首次赋值不产生任何效果。
  3. **自证性注释**：注释描述代码自身的缺陷、未使用或临时性，而非业务语义，如「最后url都没用到，直接使用的 authUrl」「临时保留，后续删除」「这行其实没用」。
  4. **注释掉的代码块**：以注释形式保留的旧实现（见 `~/.zcode/rules/annotation.md`「注释反模式」）。
  5. **恒定分支**：条件在当前执行路径下恒为真或恒为假（如 `if (false)`、被前置 return 短路后不可达的代码）。
  6. **前端未使用声明**：未使用的 import、data 字段、computed、组件注册或 CSS 选择器。
- 动作要求：
  1. 命中残留时必须整改：死赋值删除；自证性注释删除，其中承载的业务信息（如实际使用的是哪个变量、为什么）改写为对应代码段的业务注释或直接体现在代码中；注释掉的代码块删除；恒定分支按已确认的业务意图保留唯一有效路径。
  2. 删除前安全核查：检索被删变量、方法或选择器的全部引用，确认读取点为 0；赋值表达式或语句含方法调用时，确认该调用无业务副作用——有副作用时保留调用本身，仅去掉无效变量（如改为直接传参），不得连副作用一起删除。
  3. 后续逻辑实际使用的是另一变量时，以已确认的业务意图统一：要么删除死赋值，要么让后续逻辑真正使用该变量；不得保留「死赋值 + 自证性注释」的原样组合交付。
  4. 引用来自反射、框架约定、动态拼接或跨文件静态分析无法确认时，不删，保留原状并在交付「风险与未验证项」中逐处列明；本次未触及文件中的残留不在本次范围，发现时列入交付「后续建议」。
- 判断标准：本次修改触及的方法内，每个局部变量赋值语句均存在至少一个后续读取点（引用检索为据）；注释均描述业务语义，不存在描述代码自身缺陷的注释；无注释掉的代码块；无法静态确认的残留已逐处列明而非静默保留。

## 源文件字符保真

- 以 UTF-8 保存的可读源码中，中文注释、业务提示、固定中文标签及 `≥`、`≤` 等可读符号必须直接保留原字符；不得把 JSON、补丁、脚本或工具参数中的传输层 `\uXXXX` 表示原样写入源码。
- 编辑含非 ASCII 可读文本的文件后，只对本次修改文件搜索实际四位十六进制的 literal `\\u[0-9A-Fa-f]{4}` 和 Unicode 替代字符 `�`，并结合上下文与 diff 逐项确认。properties/resource bundle、协议编码、正则、测试数据或第三方生成文件确有转义语义时可以保留，但必须在审查结论中说明排除依据。

## 持久层与事务

- 新增事务只放Service；历史位置不因本次局部修复强制迁移
- 事务边界必须与已确认的完整业务操作一致，避免半成功状态；不能仅从方法长度、分层形式或设计模式推导业务原子范围
- 抽取方法、Service、组件、异步任务或设计模式不得把事务边界变化作为隐式副作用；需要扩大、缩小、拆分或跨线程事务时，必须明确列出原边界、新边界、回滚影响和工作流一致性，并按 `workflows.md` HARD-GATE 取得确认
- checked exception需要回滚时显式指定 `rollbackFor = Exception.class`
- 事务内避免同步阻塞的外部交互（发邮件、调第三方 HTTP API、消息推送等）；确需在事务内完成的数据库操作（如 BPM `completeTask` 推进）按「BPM/工作流同库参与 Spring 事务」规则处理，长耗时外部调用必须在事务提交后执行或异步化
- 批量操作前评估单条 SQL 长度（超过 1MB 或超过 5000 行参数时分批）、分批策略、索引和一致性
- 生成`IN`前短路，禁止空集合进入MyBatis `<foreach>`
- **BPM/工作流同库参与 Spring 事务**：Activiti/Flowable 表与业务表同库且共用 DataSource（`SpringProcessEngineConfiguration` 配置正确）时，`completeTask` 操作 `bpm_act_ru_*` 表参与 Spring 事务，事务回滚时工作流推进也回滚。这是避免"工作流已推进但 DB 状态未更新"一致性缺口的关键机制，但事务内不应包含长耗时操作。需先验证配置前提，非所有部署都满足

## 查询与性能

- 循环内出现getById/list/selectOne/远程调用时，先判断N+1
- 可批量时先收集主键或业务键，一次查询并按ID转Map
- 批量查询必须返回用于结果归属的主键
- 全量处理后内存分页属于明确风险；当分页结果来自单表/单条 SQL 且下推分页不改变权限范围、过滤规则、排序口径和总数含义时，改为数据库分页；无法下推时记录风险并说明原因
- 性能优化不得改变权限范围、过滤规则、排序口径和总数含义
- 性能问题按“后端接口调用链 → SQL 数量与 N+1 → EXPLAIN/索引有效性 → 分页与批量装配 → 前端 DOM 渲染与接口等待”排查；触发条件是用户报告卡顿、超时、页面无响应或接口耗时异常。未完成 SQL 数量、耗时或执行计划量化前，不得以 UI 优化替代服务端诊断；每个保留结论必须附具体指标或证据位置。具体指标至少包括查询次数、单次 SQL 耗时、`EXPLAIN` 的 `type`/`rows`/`key`/`Extra`、页面 LCP/FID/CLS 或用户报告的实际等待时间。
- 列表查询变慢时，先统计主查询、count、嵌套映射和循环调用实际产生的 SQL；分页结果逐行加载关联数据时，优先收集当前页主键批量查询，并按归属键分组回填。通过标准是列出查询次数、每类 SQL 的耗时/数量和变更前后数据归属一致。
- 索引优化必须以实际 SQL 的 `EXPLAIN`/`EXPLAIN ANALYZE` 与 `SHOW INDEX` 验证：确认 WHERE、JOIN、ORDER BY 的字段顺序能够命中索引；至少记录 `type`、`rows`、`key` 和 `Extra`。索引未命中、回表代价高或出现 filesort 时，不得宣称优化完成。
- 后端瓶颈量化完成后，再区分前端 DOM/表格渲染成本、无依赖请求并行度与异步展示策略；接口等待不能直接认定为渲染卡顿。通过标准是分别给出后端 SQL/网络耗时与前端渲染/交互证据。

## 调试前置：Touchpoint 地图

开始排查前，先列出所有入口、跨模块调用、数据库写点和外部交互，避免只分析单个方法。

判断标准：排查记录包含入口清单（每个入口的文件路径、方法/事件名）及数据库写点、外部交互清单；排查结论覆盖清单全部条目，未覆盖条目单独列出并说明原因。

## 调试前置：数据库连接

排查数据问题时，先读取主配置中的 active profile，再定位对应环境配置和数据源节点；连接信息仅用于本地查询，不得输出完整密码。

### 数据库操作授权边界

- **只读查询（SELECT 类）**：排查数据问题、字段显示异常、字典翻译缺失、关联数据或状态值核对时，自行读取主配置 `spring.profiles.active`，定位对应环境配置与 `spring.datasource.dynamic.datasource.master` 数据源节点，直接查询核实，**不再询问用户**；连接信息仅用于本地查询，不得输出完整密码。
- **变更性脚本（INSERT / UPDATE / DELETE 及常规 DDL）**：执行前必须向用户报告脚本内容与影响范围，**征得用户同意后方可执行**；未获同意不得以任何方式落地变更。
- **L3 变更（删库/删表/`TRUNCATE`/`DROP` 等强制删除或不可逆操作）**：按全局 `AGENTS.md`「操作风险与授权层级（L1/L2/L3）」处理——即使征得同意也直接拒绝，并提供备份、只读验证或人工执行的替代方案。
- **判断标准**：只读查询是否已自行核实，以「已给出脱敏后的查询条件与结果摘要」为据；变更脚本是否合法，以「用户已对脚本内容与影响范围明确同意」为据；不得把「数据库可连」表述为「已授权变更」。

## 渐进式架构治理

目标结构：请求 → Controller → Service → Mapper/DAO → DB

**新增代码**：严格遵循分层，跨模块新增调用默认走目标模块Service。优先采用设计模式（策略/工厂/模板方法等）降低复杂度，参见 `~/.zcode/rules/design-principles.md`。

**历史代码**：
- Controller已承载业务逻辑时，允许原位最小修复
- 不因历史分层问题强制重构
- 原位修复必须补足业务注释

## Spring Bean 依赖注入

- 新增 Spring Bean，或为既有 Bean 新增必需依赖时，默认使用构造注入；项目已包含 Lombok 时优先使用 `@RequiredArgsConstructor` 配合 `private final`，未包含 Lombok 时编写显式构造器。判断项目是否包含 Lombok 时以目标模块 `pom.xml`/`build.gradle` 依赖和现有源码用法为证据；单构造器无需机械添加 `@Autowired`。
- Setter 注入仅用于可选或运行期需要重新配置的依赖；字段注入不得作为新增代码的默认方式。存在多个构造器或同类型多个 Bean 时，先核对构造器签名、Bean 定义及 `@Primary`/`@Qualifier` 候选，再按 Spring 规则使用 `@Autowired`、`@Qualifier` 等明确候选关系；不得把 `@Autowired` 本身误判为废弃 API。
- 历史字段注入不得仅为统一风格批量重构；任务确需迁移时，先审查构造器签名、循环依赖、代理行为和测试实例化方式，控制回归范围。

## 导入字段与下载模板契约

- 新增、删除、重命名或修改 Excel/CSV 导入字段前，尤其是带选项/下拉的字段，必须按实际存在的触点逐项核对：录入界面或调用方及选项来源（如有） → 模板下载/模板定义（如有） → 表头、字段元数据、选项数据源和数据验证（如有） → DTO/解析映射 → 展示值与内部值转换及校验 → Entity/Mapper/Service 持久化 → 回显、查询、导出等后续消费者（如有）。
- 运行时选项控件与下载模板中的 Excel 数据验证是两个独立消费者；前者、DTO 或解析逻辑已更新，不能证明后者已同步。存在模板下载时，必须从实际下载入口追踪到模板生成或模板定义，并检查选项作用范围、起止行、空选项和无效值行为。
- 存在可下载模板且环境可运行时，至少验证实际模板的表头与选项约束，并用一个有效值、一个无效值和一个空值检查导入、内部存储值及适用的回显/查询/导出结果；环境阻断或某触点不适用时，须明确未验证项或排除依据，不得声称链路完成。

## 导出数据不一致排查

先从前端导出按钮追踪实际请求 URL，再定位对应 Controller、Service 和 Mapper；逐项对比列表查询与导出路径的筛选条件、字段映射、权限范围和空结果处理。

### 导出、导入与批量操作契约保护

## 并发优化与多线程

- 后端性能优化遇到**多个相互独立的操作**时（如多个无依赖的查询、批量装配中的辅助表查询、无数据依赖的远程调用），应评估并发多线程方案。该规则仅适用于后端服务内操作；前端请求并行按 `~/.zcode/rules/frontend.md` 处理。评估必须记录线程池/执行器、事务边界、失败聚合和取消策略；若操作共享事务、共享数据行或无可复用线程池，应记录不采用并发的原因。禁止遇到性能问题只想到加索引和缩事务。

### 何时考虑并发

| 场景 | 是否适合并发 | 原因 |
|------|------------|------|
| 多个无依赖查询（如装配列表时查字典、查用户、查组织） | ✅ 适合 | 各查询无数据依赖，可并行缩短总耗时 |
| 批量操作中的独立子任务 | ✅ 适合 | 各子任务无共享状态 |
| 有数据依赖的操作（先查后写、先读后判断） | ❌ 不适合 | 后一步依赖前一步结果，强行并发引入竞态 |
| 操作同一数据行 | ❌ 不适合 | 并发争用行锁，不如串行 + 锁机制 |
| 事务内的操作 | ⚠️ 谨慎 | 并发可能改变事务边界和锁持有时间 |

### 框架选型

- **技术栈含 Guava 时优先使用**：`ListeningExecutorService` + `Futures`/`ListenableFuture` 提供回调式异步编排，比裸 `Future.get()` 阻塞更优
- **无 Guava 时**：JDK `CompletableFuture` 或 `ExecutorService`
- **禁止**为单次优化引入新框架依赖；优先复用项目已有线程池配置

### 数据一致性优先原则（强制）

**性能优化不得以牺牲数据一致性为代价。** 并发引入后必须重新评估：

1. **乐观锁/悲观锁选型**：并发后冲突概率升高，必须按下方「并发控制机制选型」决策矩阵重新评估
2. **事务边界**：并发操作是否在同一事务内？跨线程操作同一事务会导致 Spring AOP 事务失效
3. **结果聚合的原子性**：多个并发查询结果汇总时，部分失败如何处理？是否需要降级
4. **禁止**「为保性能跳过一致性校验」：如果业务规则要求 check-then-act，必须用锁定读（FOR UPDATE）或 CAS，不能用并发绕过校验

## 并发控制机制选型

修改涉及 check-then-act（先读后写）模式时，**必须先评估并发控制机制**，禁止直接用最熟悉的方案。

### 决策矩阵

| 条件 | 推荐方案 | 理由 |
|------|---------|------|
| 单 MySQL 实例 + 低冲突 + 高操作代价 | **MySQL FOR UPDATE**（悲观锁） | 无额外依赖，锁与事务天然绑定，避免无谓重试 |
| 单 MySQL 实例 + 高冲突 + 低操作代价 | **CAS 乐观锁**（version 字段或状态条件更新） | 不阻塞读，并发冲突快速失败 |
| 跨服务 / 跨库 / 微服务架构 | **Redis 分布式锁**（Redisson） | 跨进程协调，需要续期和崩溃恢复机制 |
| RR 隔离级别 + 需要读最新数据 | **必须用锁定读**（SELECT ... FOR UPDATE） | MVCC 快照读无法读到其他事务已提交的值 |

### 评估维度（必须逐项回答）

1. **冲突概率**：同一数据行被并发操作的可能性有多高？
2. **操作代价**：冲突时重试的成本有多大（秒级 vs 毫秒级）？
3. **一致性要求**：业务不变量被违反的后果有多严重？
4. **架构约束**：当前是单体还是分布式？是否有跨库需求？
5. **改造成本**：引入新机制需要改多少代码？是否需要新依赖？

### InnoDB 行锁核心规则

InnoDB 行锁**加在索引记录上**，不是数据行上。任何 DML（SELECT FOR UPDATE / DELETE / UPDATE）的 WHERE 条件**没有可用索引** → RR 隔离级别下锁全表。加索引是消除全表锁的第一优先级。

### 性能问题技术评审流程（强制）

涉及并发控制 / 锁机制选型的性能优化，**必须完成以下技术评审**，禁止直接动手改：

1. **画并发时序图**：列出所有并发操作同一数据的请求路径（包括独立 HTTP 请求），标注锁冲突点
2. **EXPLAIN 验证**：对所有涉及锁的 SQL 执行 EXPLAIN，记录 type、rows、key 列
3. **SHOW INDEX 验证**：确认 WHERE 条件字段是否有索引
4. **量化锁持有时间**：事务内所有操作的预估耗时（查询次数 × 单次耗时）
5. **方案对比矩阵**：列出 ≥2 个方案，从改造成本、风险、性能提升、适用场景四个维度对比
6. **索引优先原则**：优化顺序——加索引（消除全表锁） > 缩事务（减少持锁时间） > 换锁机制。判断标准：每一步都先取得 `EXPLAIN`、`SHOW INDEX`、SQL 数量和事务持锁时间证据；上一步无法消除瓶颈或会引入新风险时才进入下一步，不得跳过前两步直接换锁机制。

**禁止行为**：
- ❌ 不做 EXPLAIN 就加索引（可能索引不生效）
- ❌ 不画时序图就选乐观锁（可能遗漏并发场景）
- ❌ 只优化单个触点，不审查完整调用链

### 并发防护验证清单（强制）

锁机制选型后、动手实施前，必须逐项验证，禁止假设防护已生效：

1. **自定义事务注解的实际行为**：项目自定义事务注解（如 `@HussarTransactional`）不能假设等于 Spring 标准 `@Transactional`。必须反编译或查拦截器实现，确认隔离级别（RR/RC）、传播行为、回滚规则（是否对 Exception 回滚）。悲观锁依赖事务生效，乐观锁在 RR 下有 check-then-act 陷阱，判断都依赖隔离级别，框架注解可能覆盖默认值。

2. **乐观锁三件套验证**：实体有 version 字段**不等于**有乐观锁。三件套必须齐全，缺一不生效：
   - 字段标注 `@Version`（MyBatis-Plus 乐观锁注解），不是 `@TableField("VERSION")`
   - 配置 `OptimisticLockerInnerInterceptor` 拦截器
   - 历史数据 version 有值（NULL 时 MyBatis-Plus 跳过乐观锁条件，退化成普通 update）

3. **锁范围覆盖所有写库点**：悲观锁/CAS 守护一个写点不够。必须审查完整调用链上**所有** `saveOrUpdate`/`update` 点，确认每个点要么受锁保护、要么用最新对象（非旧状态）。漏一个写点就覆盖回旧值。重点排查"中间人"方法（如 `flowFormSubmit` 内的冗余 `saveOrUpdate`），它带着旧状态对象在锁释放后写库，是并发覆盖的隐蔽元凶。

4. **事务方法调用方式**：`@HussarTransactional`/`@Transactional` 方法必须通过代理调用（跨类注入、`AopContext.currentProxy()`），不能同类 `this.xxx()`。但 `this` 调用**无注解**的基础方法（如 MyBatis-Plus `saveOrUpdate`）不影响事务；失效仅发生在 `this` 调用另一个**带注解**的事务方法时。

### jar 检索、反编译与调用链验证

1. 使用 `[System.IO.Compression.ZipFile]::OpenRead($jarPath).Entries | Where-Object { $_.Name -match "目标类名" }` 按类名搜索候选 class。
2. 使用 `[System.IO.Compression.ZipFile]::ExtractToDirectory($jarPath, $destDir)` 提取 jar；`$destDir` 必须位于当前任务可写目录，禁止写入 Maven 仓库或源码目录。
3. 使用 `Get-Command javap` 或常见 JDK 安装路径定位 `javap`；使用 `javap -c -p <class文件路径>` 反编译，`-c` 输出字节码指令，`-p` 包含私有成员；需要确认 `@ConfigurationProperties` prefix 等元数据时追加 `-v`。
4. 禁止仅凭类名、文档、常识或间接推断下确定性结论。必须从反编译输出的 `ldc`、`ldc2_w`、`sipush`、`bipush`、字段初始化或构造函数指令中读取关键参数；引用时保留类全限定名、方法名和字节码行内容。
5. 通过调用方字节码中的 `invokevirtual`、`invokestatic`、`invokespecial` 指令目标确认实际调用链；同一 jar 中存在多个同名或功能近似类时，必须区分“存在”与“接入”，禁止把未接入调用链的类当作实际实现。
6. 存在运行时数据时，使用实际数据库 ID 样本、配置值或日志按位拆解或逐项比对，并与字节码硬编码值核对；两者一致才算交叉验证通过。无运行时数据时，结论只能标注“字节码已核实，运行时交叉验证未执行”。

### 记录与结论门槛

1. 记录实际使用的 jar 文件名、路径、版本、类全限定名、方法名、字节码行内容和运行时交叉验证结果；每个关键参数必须能对应到反编译输出中的具体字节码行或常量池条目。
2. jar 不存在、构件混淆或加密、环境无 JDK、候选 jar 不唯一或提取失败时，结论中必须标注「未验证：[具体阻断原因]」，不得写入确定性表述，也不得以文档描述替代。
3. 文档与反编译结果冲突时，以反编译结果为准，并建议文档维护者更正；不得因文档更易读而回退到文档描述。
